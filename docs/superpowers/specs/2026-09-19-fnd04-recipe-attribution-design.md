# FND-04 recipe-derived aspect attribution design

## Goal and authority

Replace the live ENTROPY1 generator placeholder with intended TC6 BETA26 recipe-derived attribution on Minecraft1.20.1 Forge47.3.0/Java17. Full FND04 stays ACTIVE: this slice establishes derivation, not seed-table/NBT/bonus/consumer/progression/multiplayer parity. Base dc17c32 includes four reviewed repairs that must remain intact. Owner explicitly requires continuous fresh-builder/separate-critic work and review before commit; no repeated design permission gate applies.

REF-0015 and fnd-04-recipe-reference-evidence.md are the inspected shipped algorithm contract. Numerical expectations come from that contract, never calculated by the implementation under test. The reference pass is still subject to the final independent critic. No original implementation is copied into the repo.

## Architecture and approaches

Chosen: capture currently available recipe data for each top-level lookup, use private traversal state and per-request memoization, and compute derived base aspects without writing the explicit registration store. This follows the current port's reviewed raw-versus-computed API distinction and naturally sees reload and late registration changes. Compared with a persistent generation-aware cache it has less invalidation machinery but more repeated work; compared with registering generated values as explicit assignments it cannot permanently mask future seeds or bind early missing recipes as empty entries. A future measured performance optimization may retain this behavior, but cannot turn stale data into parity.

Keep the public AspectHelper -> InternalMethodHandler -> ThaumcraftCraftingManager route. Introduce a small recipe resolver and, if useful, a pure arithmetic helper. Internal overloads carry one query context through recursive getObjectTags/generateTags so ingredient contributions include the existing contained-aspect/bonus/culling/cap behavior without recursively starting new histories. Explicit registrations always take precedence; an opted-in container still replaces base tags. Derived base results are capped500; final computed values use the existing seven-type culling and amount cap. Never mutate input stacks, registered lists, container lists, recipe ingredients/results, or returned remainder stacks. Returned lists and memo entries cannot alias caller-owned objects.

Recipe availability has no Level parameter at the existing public API. Common code obtains the current server's RecipeManager and registry access through ServerLifecycleHooks when present. A client-only provider installed from the existing client setup supplies the current connection's RecipeManager and registry access for remote-client lookup. No common production class may import or initialize Minecraft client classes. Providers are read at query time, so disconnect/reconnect and manager replacement do not retain the old world. No connection/server means no datapack derivation; do not persist that absence. The existing legacy ThaumcraftApi catalog is also considered for supported real recipe types; fake recipes/blueprints are excluded. No new network packet or dependency.

## Recipe selection and formulas

Support loaded vanilla CraftingRecipe and IArcaneRecipe plus modern CrucibleRecipeType/InfusionRecipeType, and the existing legacy real CrucibleRecipe/InfusionRecipe/IArcaneRecipe catalog. Merge by ResourceLocation with a loaded datapack recipe winning an identical ID, then order candidates by full recipe ID. Preserve the ingredient array's first option without sorting alternatives. In1.20.1 former item variants are distinct registry items: output matching uses item identity, ignores count and arbitrary NBT, and does not mistake durability for1.12metadata.

Priority: first valid matching crucible candidate, then first valid matching infusion candidate; either category's empty non-null result still blocks crafting fallback. Ordinary and arcane crafting evaluate all matching candidates and retain the strictly smallest positive total; equal totals keep first ID order. Do not include smelting/blasting/smoking/stonecutting/smithing merely because RecipeManager exposes them. Skip unsupported dynamic outputs safely. Invalid empty/nonpositive outputs and malformed ingredients must not crash the lookup or fabricate aspects.

For ingredients, use the first matching stack once per slot, regardless of its count. Empty ingredient entries contribute nothing. Build a private3x3 synthetic crafting inventory with the same first options and invoke the actual recipe remaining-items method for vanilla/arcane candidates; use a small inventory implementing both CraftingContainer and IArcaneWorkbench where needed. Subtract remainder aspects using existing AspectList.reduce semantics: an overdraw is refused, not clamped. Infusion has no remainder subtraction. Normalize each accumulated amount using float amount*.75f/outputCount; promote only .75<v<1 to1, then truncate and remove nonpositive values.

Crucible: full catalyst aspects (not normalized/divided) plus trunc(sqrt(required)/outputCount). Infusion: normalized center+components plus the same required-essentia formula. Arcane: normalized ordinary ingredients/remainders plus MAGIC trunc(sqrt(1+integerVis/2)/outputCount) when Vis>0. Preserve integer division in Vis/2. No crystals are added as ingredient contributions. Keep arithmetic order/float behavior from REF0015 on valid supported inputs.

## Recursion and state

Count-normalize a copied stack for identity; normalize durability only for damageable items while retaining other NBT in the private history key. Use value identity, not a hash alone. Preserve shipped cumulative history across candidates/ingredients, with no branch backtracking: repeated uncached key terminates, append before traversal, and do not traverse the100th distinct key. Per-request memo reuses completed results before history checks, emulating already generated lookups within that request. Direct cycle/depth cutoffs must not themselves poison memo; only a completed enclosing result may be memoized. No persistent negative or positive cache is introduced. This is explicitly different from original cross-query cache persistence, whose premature/failed empty results can freeze absence.

## Rulings and costs

1. Per-request memo, no cross-query generated cache — prevents stale/early empty registrations and preserves reviewed raw/computed separation — cost: repeated derivation and differences from released cache-order artifacts; measure and document query work, do not claim performance acceptance.
2. Full recipe-ID ordering and datapack priority on duplicate IDs — gives a reproducible modern selection where1.12catalog iteration has no portable equivalent — cost: ambiguous equal-cost or multiple crucible/infusion outputs can differ from a particular original HashMap order. Ingredient first-choice and cumulative-history semantics remain unchanged.
3. Empty/no-recipe returns empty, with guarded malformed/cycle paths — removes fabricated ENTROPY and avoids released crash paths — cost: malformed recipes may be ignored rather than throwing; normal valid arithmetic is unchanged.

Self-review: complete formulas/priority specified; no broad NBT/seed/bonus fix smuggled in; reload isolation and original cache deviations explicit. Public release/EULA remain prohibited without owner authorization.
