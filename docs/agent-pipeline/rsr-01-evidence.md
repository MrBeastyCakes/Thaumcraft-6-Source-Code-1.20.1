## Target behaviors to capture

From the evidence-index queue row for `RSR-01` (scan-gated research completion, staged knowledge, prerequisites, and page progression) and the workboard acceptance line ("fresh player completes scan-gated entries; invalid client progress is rejected; reload preserves state"):

1. **Scan action path** — how a Thaumometer use becomes a progression event, and which side decides it.
2. **Scan gate** — what makes a scanned object count once and only once, and what scanning awards besides the research key.
3. **Requisites** — how parent research and `@stage` forms are enforced before an entry can start or advance.
4. **Stage progression** — how a stage counter advances, when an entry counts as complete, and what is granted on completion.
5. **Page progression** — what the `PAGE`, `RESEARCH`, and `POPUP` flags mean and who may set them.
6. **Client↔server authority** — which packets exist in each direction, what a client is allowed to request, and where the server re-validates and consumes.
7. **Persistence** — what survives save/reload and what a brand-new player starts with.

## Reference behavior (source-derived)

### A. The scan action and its gate

1. **The scan itself runs on the server.** `common/items/tools/ItemThaumometer.java:45-54` splits right-click by side: the client branch only draws FX and plays a sound, the server branch calls `doScan`. `doScan` (`:120-136`) re-acquires the target server-side (entity first, then a block ray-trace, then null) and calls `ScanningManager.scanTheThing`. There is no client-to-server scan packet; the client's view of the target never reaches the server as data.
2. **The manager is a first-match-any dispatch over a registry.** `api/research/ScanningManager.java:24` holds the static list of `IScanThing`; `:32-34` is the add API; `:40-82` is `scanTheThing`. For every registered thing whose `checkThing` matches, the manager calls the internal-method handler's `progressResearch` for that thing's research key and runs `onSuccess` only when that call returns true (`:43-51`). A null/empty key takes a separate branch that calls `onSuccess` and suppresses the status message for the whole call (`:44-48`).
3. **Scanning follows container contents at a bounded cost.** When the scanned object is a block position, the manager walks the block's item handler and recursively scans contained stacks, stopping after 100 stacks and reporting that the inventory is too large (`:62-80`). The helper used to turn a scanned object into an item stack (`:103-126`) also falls back to a water/lava bucket for fluid blocks (`:115-123`).
4. **The same object cannot be scanned twice for credit.** The universal scanner `common/lib/research/ScanGeneric.java` (registered at `common/config/ConfigResearch.java:148`) derives a pseudo research key from the target — `!` plus the item registry name (with damage appended for non-damageable stacks) or `!` plus the entity id (`common/lib/research/ScanGeneric.java:60-75`), and its `onSuccess` (`:38-58`) grants `OBSERVATION` knowledge to **every** research category using that category's own aspect formula. Because the pseudo key is stored in the player's knowledge set on the first scan, the second scan's `progressResearch` call fails at the already-known/complete test (see A5), so `onSuccess` does not run again and no second knowledge award occurs.
5. **A scan that cannot progress for a real research entry still costs nothing.** `ResearchManager.progressResearch` refuses when the entry is already complete or the player lacks requisites (`common/lib/research/ResearchManager.java:102-104`); the refusal propagates back to `scanTheThing`, which then skips `onSuccess` and shows the neutral "unknown object" feedback path.
6. **Aspect scans award observation points into three categories.** `api/research/ScanAspect.java:58-62` grants one `OBSERVATION` point each to the AUROMANCY, BASICS, and ALCHEMY categories when an aspect scan succeeds; other scan kinds (enchantments, potions, entities) are registered with their own `!`-keys at `common/config/ConfigResearch.java:151-163`.
7. **The "still scannable" hint is client-side and uses the loose check.** The Thaumometer's client tick (`common/items/tools/ItemThaumometer.java:56-72`) highlights the pointed target every 5 client ticks only when `ScanningManager.isThingStillScannable` returns true; that predicate (`api/research/ScanningManager.java:89-100`) tests the registered things and asks whether the player does **not** know the key, using the loose knowledge check (`api/capabilities/ThaumcraftCapabilities.java:43-57`: in-progress counts as known, `&&`/`||` supported). The server does not consult this method.
8. **The scan FX packet carries no progression data.** `common/lib/network/fx/PacketFXScanSource.java:47-50,74-122` sends a block position and a size integer, then clusters ore blocks client-side and spawns particles only; it is registered client-bound (`common/lib/network/PacketHandler.java:92`). A port that routes scan progression through this packet would be building on the wrong class.

### B. Authoritative progression

9. **Every progression entry point is guarded server-side at the handler.** `common/lib/InternalMethodHandler.java:69-72` rejects `progressResearch` when the key is null or the player's world is remote and otherwise delegates to `ResearchManager.progressResearch`; `:74-77` does the same for `completeResearch`; `:34-37` rejects `addKnowledge` for zero amounts and client-side callers. `:79-82` exposes the requisite predicate directly.
10. **The core rules live in `ResearchManager.progressResearch`.** `common/lib/research/ResearchManager.java:100-211`:
    - refuses when the entry is complete or the requisites fail (`:102-104`);
    - fires a cancellable `ResearchEvent.Research` and respects cancellation (`:105-107`);
    - records the key in the knowledge set if it is not already known (`:108-110`);
    - advances the stage counter (`:111-127`), with two auto-advance cases for stages that declare no `craft`, `obtain`, `know`, or `research` requirements (`:121-126`), and writes the stage clamped to the stage count plus one (`:127`) so "complete" is representable;
    - applies stage warp through the internal handler, splitting warps greater than one between permanent and normal warp and honoring the misc-config `wussMode` switch (`:129-154`);
    - only when the entry reaches its final stage, sets the `POPUP`/`RESEARCH` flags, grants reward items, and grants reward knowledge through `addKnowledge` (`:156-177`);
    - then scans all categories for addenda that name the newly completed key and flags those completed entries with `PAGE` (`:178-194`);
    - cascades completion into siblings that are not complete and pass the requisite test (`:197-203`);
    - queues the player for a knowledge sync and awards 5 experience (`:204-209`) — but only when the scanned key exists as an entry in the research registry (`if (re != null)`, `:206-207`), so a `!`-pseudo-key scan awards no experience.
11. **Completion is a loop.** `completeResearch` (`:70-84`) repeatedly calls `progressResearch` until it returns false, which is how a stage chain is consumed in one call; `startResearchWithPopup` (`:86-94`) starts an entry and sets both the popup and new-research flags.
12. **Requisites are parent-based and strict.** `ResearchManager.doesPlayerHaveRequisites` (`:213-220`) looks up the entry, returns true when the entry is unknown to the research registry (this is why `!`-pseudo-keys always pass), and otherwise requires the entry's stripped parents to be known under the strict check (`api/capabilities/ThaumcraftCapabilities.java:70-88`): complete-only, unless a parent carries an `@` stage suffix, in which case the loose, stage-aware check applies.
13. **Craft requirements are satisfied by a crafting event, not by the scan.** Stage `required_craft` entries are hashed at research-load time and collected in a static set (`common/lib/research/ResearchManager.java:361-375` and `:606`). A `PlayerEvent.ItemCraftedEvent` listener hashes the crafted stack (twice, with and without count/damage) and each of its ore-dictionary names, and calls `completeResearch` for any matching `[#]`-prefixed key (`common/lib/events/CraftingEvents.java:49-74`).
14. **Knowledge points are raw counters read through a divisor.** `api/capabilities/IPlayerKnowledge.java:151-153` defines `THEORY` with progression 32 and `OBSERVATION` with 16 (both marked as having category fields); the stored value is raw and the readable value is a floored division by that constant (`common/lib/capabilities/PlayerKnowledge.java:171-198`), keyed by type abbreviation plus category key. `ResearchManager.addKnowledge` (`:50-68`) fires a cancellable `ResearchEvent.Knowledge`, adds the raw amount, and sends one knowledge-gain packet per progression unit gained, then queues a sync.
15. **Theorycrafting converts to theory knowledge on the server.** `common/tiles/crafting/TileResearchTable.java:84-98` turns the solved page's category totals into `THEORY` knowledge through the internal handler, with a penalty multiplier for categories past the penalty start. Full research-table behavior belongs to `RSR-03`; it is listed here only because `required_knowledge` stages are paid from this pool.

### C. Client/server surfaces

16. **Server→client state sync is a single full snapshot.** `PlayerKnowledge.sync` (`:200-203`) sends `PacketSyncKnowledge`, whose constructor serializes the sender's whole knowledge state and clears the `POPUP` flags at the source before sending (`common/lib/network/playerdata/PacketSyncKnowledge.java:29-35`). The client handler deserializes, then for each entry that still carries a `POPUP` flag looks up the research entry and raises a research toast, clearing the flag afterwards (`:45-65`). Registered client-bound at `common/lib/network/PacketHandler.java:70`.
17. **The one client→server progression packet is fully re-validated and pays costs server-side.** `common/lib/network/playerdata/PacketSyncProgressToServer.java` carries a key, a boolean "the client believes it does not know this", and two option flags. Its server handler (`:55-73`) runs on the server thread, ignores the request unless the client's belief differs from the server's knowledge state (`:61`), and — when checks are requested — runs `checkRequisites` (`:75-147`) before calling `ResearchManager.progressResearch` (`:68`). `checkRequisites` verifies, in order:
    - that the player currently carries every `obtain` entry of the current stage, using an ore-aware carrying test (`:86-102`), and then **consumes those entries server-side** (`:103-115`);
    - that each `required_craft` hash is known as `[#]`-plus-hash (`:117-124`);
    - that each `required_research` is strictly known (`:125-132`);
    - that the player holds the stage's knowledge points, then **deducts** them (`:133-144`).
    Only the research GUIs send this packet: `client/gui/GuiResearchBrowser.java:807` and `:818`, and `client/gui/GuiResearchPage.java:1534`.
18. **Flag changes are the only other client-driven write, and they are display-only.** `common/lib/network/playerdata/PacketSyncResearchFlagsToServer.java` builds its payload from the client's own flag state (`:22-25`) and its server handler sets or clears exactly the `PAGE`, `POPUP`, and `RESEARCH` flags for one key (`:37-67`). It cannot add research, set a stage, or change knowledge — so a client can tidy its own UI flags but cannot fabricate progression. The GUI sends it when the player opens a known entry (`client/gui/GuiResearchBrowser.java:812-815`).
19. **Knowledge-gain feedback is a broadcast-only cosmetic.** `common/lib/network/misc/PacketKnowledgeGain.java:54-62` pushes a HUD knowledge-gain tracker plus a learn sound on the client; registered client-bound at `PacketHandler.java:55`. It carries no state that the server trusts back.
20. **Entry into the loop is a block-triggered action gated on known research.** `common/config/ConfigRecipes.java:71-75` registers dust triggers that swap a bookshelf for a Thaumonomicon and a crafting table for an arcane workbench. The trigger semantics are in `common/lib/crafting/DustTriggerSimple.java:29-44`: the trigger is valid only when the target block matches **and the player already knows the trigger's key** (so `!gotdream` and `FIRSTSTEPS@1` are preconditions, not grants), and its execution fires a player-crafting event and then swaps the target block with the result stack. Which mechanic grants those keys, and therefore what a fresh player can dust, is part of the starting state that C1 must observe rather than assume. These are original recipe registrations, useful for the checklist below; the research JSON that defines the keys is outside this note.

### D. State model

21. **A player's knowledge is four parallel stores.** `PlayerKnowledge` keeps a research key set, a stage map, a flag map, and a raw knowledge map (`common/lib/capabilities/PlayerKnowledge.java:48-58`); `clear()` empties all four (`:61-66`).
22. **Status is derived, and unknown entries count as complete.** `getResearchStatus` (`:68-78`) returns UNKNOWN when the key is not known, otherwise COMPLETE when the registry has no entry or no stages, or when the stored stage exceeds the stage count, else IN_PROGRESS. This is the mechanism behind the `!`-pseudo-key behaviour in A4: pseudo-keys are absent from the registry, so they are complete the moment they are known.
23. **Stage and known semantics.** `getResearchStage` (`:97-104`) returns -1 for a key that is not known and 0 for a known key without a stored stage; `setResearchStage` (`:106-113`) refuses null, unknown, or non-positive stages; `isResearchKnown` (`:80-90`) treats null as unknown, the empty string as known, and honours the `@stage` suffix by comparing against `MathHelper.getInt`; `addResearch` (`:115-122`) only adds a key that is not already known.
24. **Persistence is a full snapshot with flags packed as text.** Serialization (`:205-242`) writes the research list with optional stage and a comma-joined flag string, plus every knowledge entry whose raw amount is positive and whose key is non-empty. Deserialization (`:244-284`) clears first, re-adds research with stage and flags, restores knowledge, and then runs the auto-unlock pass — so a load can never accumulate duplicates.
25. **Auto-unlock research is (re)granted on every deserialization.** `:286-294` iterates all categories and adds every entry carrying the `AUTOUNLOCK` meta. Because deserialization runs on both sides, this is also what a brand-new player's loaded-but-empty capability receives, which is the source-derived explanation for the starting set of entries (**unverified — needs rank-1 observation** for the exact set and its visibility).
26. **Flags have distinct meanings.** `api/capabilities/IPlayerKnowledge.java:179-186` documents `PAGE` as "this research has a new page", `RESEARCH` as "new and not yet examined", and `POPUP` as "trigger a GUI popup when synced; cleared once sync occurs". Flag setting and clearing are implemented at `common/lib/capabilities/PlayerKnowledge.java:139-169`, including the duplicate-set guard; the flag-map cleanup at `:158-160` is an implementation artifact rather than a functioning cleanup — `flags.remove(research)` passes the research-set field object instead of the flag-map key, so the removal never matches a map entry and is a no-op that leaves the emptied flag list in the map.
27. **The capability is registered with a default implementation** (`PlayerKnowledge.preInit`, `common/lib/capabilities/PlayerKnowledge.java:32-44`) and is exposed through a provider keyed on the knowledge capability (`:297-328`), which is how recipes and GUIs read it via `ThaumcraftCapabilities.getKnowledge`.

## Rank-1 capture checklist

Reference setup for every step: a clean 1.12.2 instance whose only mods are the BETA26 jar and Baubles (see `REF-0002` and the "Environment feasibility" section of [reference-catalog.md](reference-catalog.md)); record the profile, world seed, and game mode in a new `REF` entry before starting. Single-player first, then the multiplayer pass. Operator commands referenced below are op-only (`common/lib/CommandThaumcraft.java:51`) and exist for setup, not for the observations; note that the grant form adds the entry **and its parents** and drives them to complete (`common/lib/CommandThaumcraft.java:181-215`), so it cannot produce a partially-staged entry, while `revoke` removes the named key and recursively revokes every **complete** entry that lists it as a parent — a complete-only cascade (`common/lib/CommandThaumcraft.java:236-268`: the revoked key must already be complete, `:255`, and a child is cascaded into only when the child is complete, `:258`), so in-progress children survive; the command reports the research and its children as removed (`:240`). It is the lever for the prerequisite checks.

- **C1 — Fresh player start state.** New world, new player: record which Thaumonomicon entries are visible before any scan. Then test the starting chain as an observation rather than an assumption: record whether a fresh player can dust a bookshelf or a crafting table at all (the trigger requires its key to be already known, item 20), and if it can, what the target block becomes and what the Thaumonomicon/arcane-workbench access looks like. Finish by confirming the arcane workbench is obtainable and its early recipes appear. Confirms item 20 and the auto-unlock surface (item 25).
- **C2 — A scan completes and awards.** With a Thaumometer, scan one never-scanned object: record the action-bar text, the appearance of the entry in the browser, the toast on the next knowledge sync, and — for a scan that advances a real (registry) entry rather than a `!`-pseudo-key, which awards no experience — the 5-experience award (item 10). Then scan the *same* object again: expect no second award and no state change (items 4 and 5).
- **C3 — Container contents scan.** Place the object inside a chest and scan the chest: confirm the contained object is scanned by the same path (item 3). The sub-check for a chest holding more than 100 stacks is **source-derived only and NOT observable in the clean reference profile**: the scan trips at 100 scanned non-empty slots with the "inventory too large" message (`api/research/ScanningManager.java:66-76`), while a vanilla chest exposes 27 slots (54 doubled), so observing it would require a container with 100+ slots (e.g. a modded `IItemHandler`), which the declared BETA26 + Baubles setup excludes.
- **C4 — Knowledge feedback.** Watch the HUD knowledge tracker and listen for the learn sound while scanning novel objects, and record a bounded tally of tracker entries against the number of progression units a scan should award. Exact counting is not practical from the HUD alone; record the observed count for a fixed set of scans instead (item 14).
- **C5 — Obtain-requirement stage.** Park an entry on a stage whose required item is not carried: click the page's complete button and confirm nothing changes. Then carry the item and click again: confirm the stage advances, the item is consumed exactly once, and the count drops by the required amount (item 17).
- **C6 — Craft-requirement stage.** For a stage that requires crafting an item, confirm the stage cannot advance before that craft and can after it, and that the craft must be the matching item (item 13).
- **C7 — Knowledge-cost stage.** Solve research-table pages until the entry's knowledge requirement is met, then complete the stage and confirm the knowledge is deducted by the stated amount — this is the observable half of item 17's knowledge branch (item 15).
- **C8 — Prerequisite gate.** The entry under test must be known and **IN PROGRESS** when the parent is revoked — if it is complete, the revoke cascade deletes it and a re-grant trivially completes it again, degenerating the check; an in-progress child survives the cascade (`common/lib/CommandThaumcraft.java:236-268`). With `/thaumcraft research <player> revoke <parent>` remove the parent of an in-progress entry: confirm the entry survives and can no longer be started/advanced, then re-grant the parent and confirm progress resumes. Also exercise the `@stage` form: find a stage that requires a parent at a specific stage and confirm the requirement is unmet until the parent reaches that stage (items 12 and 23).
- **C9 — Persistence and reload.** Before quitting, note the stage, the flag state, and the knowledge display for one entry. Quit to title and reload the world: confirm all three are unchanged, that no popup toast repeats for an already-seen popup, and that flags the player cleared stay cleared (items 16, 24, 26).
- **C10 — Multiplayer authority.** Run a dedicated server with two clients. Player A completes a stage that requires carried items; player B opens the same entry page and clicks complete without carrying them: confirm B does not advance. Then have B carry the items and complete: confirm B's items are consumed on the server (check A's view of B's inventory or B's own counts after re-log) (item 17). Also confirm a second client that joins later receives the current knowledge state on login (item 16).
- **C11 — Client-led progress cannot skip costs.** As a bounded negative test, drive the GUI through its normal button with requirements deliberately missing (no carried items, insufficient knowledge, parent revoked) in three separate runs and confirm all three produce no state change and no item consumption. This is the rank-1 counterpart of the defect sentence "accept client-led progress" in `deferred-issues.md`.
