## Reference behavior (source-derived)

### A. The seal item and the placed seal

1. **One item, many variants, and the metadata is the registration order.** The seal placer registers under the item name `seal` with a `blank` base (`common/golems/seals/ItemSealPlacer.java:20-27`: stacks to sixty-four, subtypes on, no damage), and all variants — blank plus one per registered seal — are served on the mod's creative tab (`:29-37`; the base item class puts every item on that tab and lists all metadata values there, `common/items/ItemTCBase.java:17-23`, `:44-54`; registration `common/config/ConfigItems.java:282`). The variant list is computed live: index zero is the blank, then every registered seal key with its prefix trimmed off (`common/golems/seals/ItemSealPlacer.java:39-58`), and both directions of the mapping — key to stack and key to drop metadata — come from the live registry order (`:60-70`; drop side `common/golems/seals/SealHandler.java:103-111`), so reordering registrations renumbers every seal item and every recipe and drop that names a seal. The player-facing names are the Blank Seal and sixteen Control Seal names (`assets/thaumcraft/lang/en_us.lang:216-232`).
2. **The registry is an ordered map with duplicate protection.** Seal types live in a linked map keyed by the seal's own key string, and registering a key twice is refused with a log error rather than replaced (`common/golems/seals/SealHandler.java:30-50`). Sixteen seals are registered in a fixed order at pre-init — collect, advanced collect, store, advanced store, empty, advanced empty, harvest, butcher, guard, advanced guard, lumberjack, block breaker, use, provide, stock, advanced block breaker (`common/config/ConfigItems.java:309-326`, called from `Registrar.java:58`) — and that same order is the item variant order and the drop-value order above.
3. **Placement binds a seal to one block face.** Right-clicking a block face with a seal variant (not sneaking, not the blank) asks the seal whether it can sit there and then registers it at that block position and face (`common/golems/seals/ItemSealPlacer.java:72-94`); sneaking bypasses placement so blocks can still be placed, and the blank variant does nothing (`:73`, `:96-98`). A face that already carries a seal is refused silently — no seal appears and no item is consumed, because the item only shrinks after a successful registration (the registration refusal `common/golems/seals/SealHandler.java:146-154`; the shrink gated on success `common/golems/seals/ItemSealPlacer.java:90-92`). Survival placement consumes one item; creative does not (`common/golems/seals/ItemSealPlacer.java:90-92`). The placed seal records its owner as the placing player's account identifier string (`common/golems/seals/SealHandler.java:155-156`).
4. **A seal is ethereal: no block, no entity — a map entry plus an icon.** The research page states the intent — a seal can share its block with a placed block and several seals may share one block space on different faces, and seals stay visible while a seal, a golem placer, or the Golemancer's Bell is held (`assets/thaumcraft/lang/en_us.lang:1702`). Mechanically, a placed seal is an entry in the handler's per-dimension map keyed by block position and face (`common/golems/seals/SealHandler.java:30-33`; key identity `api/golems/seals/SealPos.java:6-43`), and its only in-world presence is a client-rendered icon drawn while a displayer item is held (`api/golems/ISealDisplayer.java:1-11`; render gate `client/lib/events/RenderEventHandler.java:432-437`; drawing with a sixteen-block fade, a see-through mode while sneaking, and a spark on redstone-stopped seals `:461-489`).
5. **The settings live on the placed seal, not on the item.** The item stack carries only its variant metadata; each placed seal is an object holding the seal position, the seal instance, priority, colour, locked, redstone-sensitivity, owner, a redstone-stopped flag, and an area that defaults to three-by-three in the plane perpendicular to its face (or one-by-one-by-one when the seal does not declare an area interface) (`common/golems/seals/SealEntity.java:19-57`). Serialization puts everything under one compound: position and face, the seal type key, priority, colour, locked, redstone, owner, the seal's own custom data, the area, and each declared toggle by its key (`:172-195`), with the matching read path rebuilding the seal from its registered class and reapplying custom data, area, and toggles (`:144-170`).
6. **Attachments are validated, and a seal whose host stops fitting is removed.** Each seal answers `canPlaceAt` for itself — the container-attached seals require an item handler on the target face (`common/golems/seals/SealEmpty.java:100-104`; `common/golems/seals/SealProvide.java:221-225`), the collection seal declares the area interface and scans that box for dropped items (`common/golems/seals/SealPickup.java:32`, `:51-89`) — and the handler re-checks every twenty ticks, removing any seal whose host no longer fits and any seal whose tick throws (`common/golems/seals/SealHandler.java:184-208`, especially `:194-197` and `:203-205`).

### B. Per-level storage and reload survival

7. **The live map is in memory, per dimension.** `SealHandler.sealEntities` is a static map from dimension to a concurrent map of position-plus-face to seal entity, initialised empty and never serialised as a whole (`common/golems/seals/SealHandler.java:30-33`, `:221-226`); the accessors either return the stored entry or lazily create an empty layer for the dimension (`:132-144`), and the range and chunk queries scan that layer with null and distance guards (`:52-89`). The world-tick driver walks every seal whose chunk is loaded and removes on exception (`:184-208`); each seal itself skips its tick while redstone stops it (`common/golems/seals/SealEntity.java:60-81`), driven from the world tick at `common/lib/events/ServerEvents.java:173`.
8. **Durability is each chunk's own save data — there is no world-saved-data class.** On a chunk save, the mod writes its whole payload into the chunk's own tag under a single `Thaumcraft` compound: the regeneration flag, the aura chunk's base, flux, and vis, and a list of the chunk's seals, each one a per-seal compound produced by its writer (the format of item 5), and any seal belonging to a chunk that is not loaded is dropped from the in-memory map only after it has been written (`common/lib/events/ChunkEvents.java:27-52`). On a chunk load the list is read back: each compound rebuilds a seal entity through the read path and re-registers it with the handler, so the map refills lazily with chunk loading (`:54-90`, seals at `:68-77`). A whole-tree search finds no world-saved-data, per-world-storage, or map-storage class anywhere — chunk save data is the only file the seals ever reach.
9. **What makes the save happen is the aura system's dirty-chunk queue.** Every registration, removal, and creation path marks the containing chunk dirty by adding it to the aura handler's dirty-chunk list (`common/golems/seals/SealHandler.java:210-219`, called from `:127`, `:160`, `:179`; the list itself `common/world/aura/AuraHandler.java:23`), and once every twenty ticks the server walks that list, marks each chunk dirty on the world so vanilla will save it, and clears the list (`common/lib/events/ServerEvents.java:157-164`). So a seal change is durable only after that sweep plus the game's own chunk save — the practical guarantee a rank-1 pass must probe (T6).
10. **Teardown and reload.** On world unload the dimension's whole seal layer is dropped (`common/lib/events/WorldEvents.java:33-38`), and nothing persists in memory across the restart; after the reload the seals return as their chunks load (item 8). A seal in a chunk that has not yet been loaded is therefore neither visible nor reachable by the bell — the handler simply has no entry for it yet.
11. **The client keeps its own copy, fed by two packet paths.** Adding or removing a seal sends a packet to the whole dimension (`SealEntity.syncToClient` `common/golems/seals/SealEntity.java:197-202`; send sites `common/golems/seals/SealHandler.java:158-161`, `:123-125`), and every player who starts watching a chunk is sent one packet per seal in it (`common/lib/events/ChunkEvents.java:92-97`). The packet carries position, face, the seal key or a removal marker, priority, colour, locked, redstone, owner, the area when the seal uses one, each toggle value, and the filter list with per-slot sizes (`common/lib/network/misc/PacketSealToClient.java:44-96`); the client handler either removes its local copy or rebuilds a full local seal from the registered class and re-applies everything (`:135-171`). Client rendering and the bell's search both read this client-side copy (items 4 and 14).

### C. The Golemancer's Bell

12. **One item, stack of one, and it is one of the three reveal items.** The bell is a plain single-variant item that stacks to one and declares itself a seal displayer (`common/golems/ItemGolemBell.java:26-32`), registered among the mod's items (`common/config/ConfigItems.java:280`), named the Golemancer's Bell (`assets/thaumcraft/lang/en_us.lang:214`). Its recipe is an ordinary shaped craft of quartz and sticks — not a research-gated station recipe — and the control-seal research stage lists the bell and the blank seal as its bookmarks (`common/config/ConfigRecipes.java:467`; `assets/thaumcraft/research/golemancy.json:94-101`). As a displayer it joins the golem placer and the seal placers as the only item classes that make placed seals visible (`client/lib/events/RenderEventHandler.java:432-437`; research text `assets/thaumcraft/lang/en_us.lang:1702`).
13. **Right-click outcomes.** On the server, when the player's block-reach trace lands on a block or an entity, the bell searches for a seal along the look ray: a hit while sneaking removes it with a zap sound, a hit otherwise opens the seal screen; a miss while sneaking and knowing the logistics research opens the logistics screen; nothing else happens (`common/golems/ItemGolemBell.java:34-60`). The block-click hook mirrors the same outcomes for the clicked face (`:62-82`). The client side of the right-click plays a pickup sound instead (`:56-58`). A removal spawned by either hook returns the seal as its variant item on the face it occupied and suspends every task that referenced it (`common/golems/seals/SealHandler.java:102-112`, `:117-122`). The guard that gates this branch accepts a block or entity hit, but the tracer it calls only ever reports block hits or nothing, so the entity half of that condition never fires on this path (`common/golems/ItemGolemBell.java:37-38`; the tracer `codechicken/lib/raytracer/RayTracer.java:153-162`).
14. **The seal search walks the look ray and tests faces.** The bell samples the look direction from the eye in half-block steps, bounded at fifty steps even though the segment the per-step test resolves against is only five blocks long, and at each sampled block it computes which face of that block's box the eye-to-five-block segment crosses first and asks the handler for a seal bound to exactly that face; the first match along the ray wins (`common/golems/ItemGolemBell.java:84-113`). The face-crossing arithmetic is a local port of the vanilla block-trace shape: six plane intersections filtered by their bounds and the nearest kept (`:115-125`, `:127-194`). What a player can therefore click is a seal whose occupied face the five-block look segment crosses — the same nominal reach the retrace guard uses.
15. **The bell on a golem is the golem's own code.** Aiming the bell at a golem and right-clicking toggles its follow mode, but only when the thrower knows the direct-control research, and sneak-picking a golem up returns the golem placer item with its properties and experience — both branches live in the golem entity and are cross-referenced to `AUT-02`, not re-derived here (`common/golems/EntityThaumcraftGolem.java:430-467`; player strings `assets/thaumcraft/lang/en_us.lang:697-698`; research text `:1706`).
16. **Both screens are re-resolved at open time, not passed by coordinates.** Opening the seal screen (identifier eighteen) makes both sides re-run the bell's seal search at that moment — the client builds the seal's own screen from the fresh result, and the server builds the seal's own container from its own fresh result, so if the server's trace no longer finds a seal the container comes back empty and the screen cannot open (`proxies/ProxyGUI.java:113-119`, `:182-188`; the seal supplies both objects, `api/golems/seals/ISeal.java:51-54`; the filtered base returns the shared screen and container, `common/golems/seals/SealFiltered.java:72-81`). The logistics screen (identifier twenty) takes its delivery target from the client's own trace at open time and treats a failed trace as deliver-to-player (`proxies/ProxyGUI.java:120-129`; `client/gui/GuiLogistics.java:60-77`).

### D. The configuration screen

17. **The screen is a category ring over a shared container.** The seal screen is a container screen of the standard size with a texture, and around its centre it draws one button per category the seal declares, plus a redstone toggle button that every seal gets (`common/golems/client/gui/SealBaseGUI.java:45-60`, `:72-96`); a seal that declares no categories falls back to priority and requirements (`:56-59`), and the container falls back to priority only (`common/golems/client/gui/SealBaseContainer.java:51-56`). The category vocabulary is fixed in the API: priority/locking zero, filter one, area two, options three, requirements four (`api/golems/seals/ISealGui.java:4-11`).
18. **What each category exposes.** Priority/locking shows the priority figure with a stepper pair, a colour swatch with a stepper pair whose zero state reads "all golems", the lock toggle, and — through the always-present separate button — the redstone flag; filter draws a ghost-slot grid sized by the seal's filter size plus a blacklist toggle; area draws three labelled steppers for the axes; options draws one checkbox per declared toggle, laid out by count; requirements draws the seal's required and forbidden trait icons with hover help (`common/golems/client/gui/SealBaseGUI.java:97-166`; captions and labels `assets/thaumcraft/lang/en_us.lang:807-818`; legend `:836-846`).
19. **The container is the edit channel, and the server applies every button.** The container builds its category set from the seal, lays the player inventory underneath, and answers the interaction check with a constant true — there is no ownership gate and no distance gate in the container itself (`common/golems/client/gui/SealBaseContainer.java:42-58`, `:93-106`). Button presses travel as the container's enchant-item channel and the server applies them: category switching, on/off pairs for each toggle, lock and unlock, redstone on and off, whitelist and blacklist, the priority stepper clamped to minus five through plus five, the colour stepper clamped to zero through sixteen, and the three area steppers clamped to one through eight per axis (`:108-180`). Priority, colour, and area values come back to the open screen as window properties, and the filter grid is written through the ghost slots (`:182-237`). Nothing in this channel is broadcast to other watching clients — the change surface for anyone else is only the add/remove packet path of item 11.
20. **Filter editing is ghost-slot editing.** The filter slots hold a copy of what the player drops on them — the cursor stack is never consumed: left-click with a carried stack stamps it (starting its size limiter at zero, or adding the carried count to an existing matching limiter), left-click with an empty hand raises a limiter by one (ten with quick-move), right-click with an empty hand lowers it by one and clears at zero, and right-click with a carried matching stack subtracts the carried count (`common/golems/client/gui/SealBaseContainer.java:239-311`). The limiter is only meaningful where the seal switches it on: the filtered base reports none, the store seal tunes them to whitelist mode, and the stock seal always uses them (`common/golems/seals/SealFiltered.java:133-136`; `common/golems/seals/SealFill.java:169-172`; `common/golems/seals/SealStock.java:109-112`); in whitelist mode the slot draws its count with a gold star for zero (`common/golems/client/gui/SealBaseGUI.java:290-322`; base defaults `common/golems/seals/SealFiltered.java:23-33`, `:88-91`; a nine-slot provider example `common/golems/seals/SealProvide.java:49-52`).
21. **Defaults live in the seal classes.** Each seal's constructor builds its toggle set with default values and its filter array with its own size (collect `common/golems/seals/SealPickup.java:39-44`; empty `common/golems/seals/SealEmpty.java:32-38`; provide `common/golems/seals/SealProvide.java:38-42`); the filtered base defaults to a one-slot filter in blacklist mode (`common/golems/seals/SealFiltered.java:29-33`); the entity defaults are priority zero, colour zero, unlocked, redstone-ignorant, no owner, and the face-derived area (`common/golems/seals/SealEntity.java:31-57`); and each seal decides its own category list — the filtered base falls back to priority only (`common/golems/seals/SealFiltered.java:83-86`), empty declares filter, priority, and requirements (`common/golems/seals/SealEmpty.java:115-118`), collect declares area, filter, priority, and requirements (`common/golems/seals/SealPickup.java:159-162`), and provide declares filter, options, priority, and requirements (`common/golems/seals/SealProvide.java:232-235`) — which is what its screen shows.

### E. Ownership, priority, and colour

22. **The owner is recorded once, at placement, and displayed back.** Registration stamps the placer's identifier onto the seal (`common/golems/seals/SealHandler.java:155-156`), it travels in the save format and the sync packet (`common/golems/seals/SealEntity.java:152`, `:182`; `common/lib/network/misc/PacketSealToClient.java:70`, `:163`), and the screen prints the "you own this seal" line only for the matching player (`common/golems/client/gui/SealBaseGUI.java:209-213`; string `assets/thaumcraft/lang/en_us.lang:839`).
23. **The lock is the enforcement point, and it is enforced by golems, not by players.** A locked seal only accepts its tasks from golems whose owner identifier equals the seal's owner string; both the golem-side task validation and the provider seal's own task validation test exactly this (`common/golems/ai/AIGoto.java:131-148`, the lock test at `:136`; `common/golems/seals/SealProvide.java:193-211`, the lock test at `:197`). The two player-facing strings describe the locked state as restricted to the seal owner's golems and the unlocked state as open to all golems (`assets/thaumcraft/lang/en_us.lang:840-841`).
24. **Configuration and retrieval are not ownership-gated server-side.** The container applies every button with no owner test (item 19), and removal has no owner test at all — any bell holder who sneak-clicks a seal removes it, and the seal item drops at the face it occupied (`common/golems/seals/SealHandler.java:91-130`; `common/golems/ItemGolemBell.java:41-44`, `:67-70`). The ownership sits entirely on the client side of the screen: only the lock and redstone buttons check the owner before flipping their local value, and only the owner sees the owner line (`common/golems/client/gui/SealBaseGUI.java:265-268`, `:279-282`, `:209-213`); a non-owner's press of those two buttons still transmits through the generic branch that forwards the raw button identifier (`:283-285`), and the logistics screen's item list is likewise filtered to the viewer's own provide seals within thirty-two blocks (`common/container/ContainerLogistics.java:61-105`, especially `:66-68`).
25. **Priority and colour chain from the seal into task ordering and eligibility.** The seal's priority, clamped minus five through plus five with default zero, is copied onto every task the seal mints (`common/golems/seals/SealEmpty.java:61-65`; steppers item 19); the task sorter subtracts two hundred fifty-six times the priority from the squared golem-to-target distance, so one priority step moves a task's effective pull by about sixteen blocks (`common/golems/tasks/TaskHandler.java:49-80`, `:82-116`); and a colour task is rejected for a golem only when both the golem and the seal carry a colour and they differ (`api/golems/tasks/Task.java:140-148`). The research page states both rules in player terms (`assets/thaumcraft/lang/en_us.lang:1702`).

### F. Task creation at the seal level

26. **The handoff object is a task ticket minted by the seal.** A task carries its seal position, a target block or entity, an identity hash derived from the seal and target, a type that distinguishes block from entity work, a priority, a lifespan in seconds defaulting to three hundred, a reservation flag that extends it, a suspension flag, a completion flag that extends it, a data slot, and an optional link to a provision request (`api/golems/tasks/Task.java:13-54`, `:64-113`, `:140-148`); tasks live in a per-dimension map capped at ten thousand entries, evicting an arbitrary map-order entry on overflow rather than by age (`common/golems/tasks/TaskHandler.java:17-36`).
27. **Seals mint tasks from their own tick loops, with their own cadence and filters.** The empty seal, every twenty ticks, finds a matching stack in the inventory it is attached to, mints a block task at its own position carrying its priority and a five-second lifespan, and remembers the stack under the task identity (`common/golems/seals/SealEmpty.java:45-67`); the collect seal scans its configured area every five ticks for dropped items and mints an entity task for the first matching drop it finds (`common/golems/seals/SealPickup.java:51-89`); the store, use, lumberjack, breaker, guard, butcher, and harvest seals follow the same shape with their own targets (`common/golems/seals/SealFill.java:50-63`; `common/golems/seals/SealUse.java:60`; `common/golems/seals/SealLumber.java:66-68`; `common/golems/seals/SealBreaker.java:71-74`; `common/golems/seals/SealGuard.java:64-67`; `common/golems/seals/SealButcher.java:72-75`; `common/golems/seals/SealHarvest.java:101-110`).
28. **The golem side is cross-referenced, not re-derived.** Task selection sorts by distance-minus-priority per type and hands the chosen ticket to a golem through its AI; completion routes back through the owning seal's completion hook; and the periodic sweep drops suspended or expired tasks and notifies the seal (`common/golems/tasks/TaskHandler.java:49-116`, `:118-129`, `:131-148`). What the golem then does with the ticket — navigation, work, carry limits, upgrades, and the multiplayer behaviour of all of it — is `AUT-02`.
29. **Tasks are deliberately ephemeral; the seal is what survives.** Nothing in the chunk save path serialises tasks — the chunk payload holds aura values and seals only (item 8) — and the task class's own save and load methods are commented out in the tree (`api/golems/tasks/Task.java:169-223`). After a reload the seals return (item 8) and their tick loops mint fresh tasks as conditions recur; the five-second and three-hundred-second lifespans and the once-per-second drop sweep bound how long an orphaned ticket can linger (`common/golems/tasks/TaskHandler.java:131-148`; `common/golems/seals/SealEmpty.java:63`).
30. **Provision requests are the cross-seal handoff.** Seals that need something publish a request instead of a ticket — the harvest seal requests a replant item, the stock seal requests restocking, the use seal requests a consumable (`common/golems/seals/SealHarvest.java:183-188`; `common/golems/seals/SealStock.java:52-56`; `common/golems/seals/SealUse.java:130-135`) — and requests live in a per-dimension list, deduplicated, capped at a thousand, and marked invalid when their linked task dies (`api/golems/GolemHelper.java:44-136`; expiry marking `common/golems/seals/SealProvide.java:56-64`). The provide seal matches a request against its own filter and its inventory's surplus within sixty-four blocks, mints the pickup task borrowing the requesting seal's priority, and, when the item is taken, mints a second delivery ticket aimed at the requester's position or entity (`common/golems/seals/SealProvide.java:54-97`, `:104-181`, the delivery ticket at `:131-146`).
31. **The logistics screen is the player-facing front of the provision chain.** Its container aggregates the items reachable through the viewer's own provide seals within thirty-two blocks, deduplicated, filtered, and paginated (`common/container/ContainerLogistics.java:61-105`, `:107-127`; lookup `common/golems/seals/SealHandler.java:52-69`); clicking an entry and pressing request sends one server packet carrying the clicked block and side (or nothing for an air click), the chosen stack, and a count (`client/gui/GuiLogistics.java:174-217`, request at `:195-215`); the handler turns each stack into provision requests, after which the provide-seal and golem machinery above must deliver — delivery completion is `AUT-02`'s verification (`common/lib/network/misc/PacketLogisticsRequestToServer.java:55-79`; strings `assets/thaumcraft/lang/en_us.lang:1099-1100`; research text `:1710`).
32. **Dormant plumbing a port must not copy as live behaviour.** The dedicated filter packet is registered but never sent anywhere in the tree — no constructor call exists — so filter state reaches clients only through the general seal packet and the editing container (`common/lib/network/misc/PacketSealFilterToClient.java:18-78`; registration `common/lib/network/PacketHandler.java:67`; send sites, none, in contrast to the general packet's registration `:66`); and the bell's right-click gate contains an entity clause its tracer can never satisfy (item 13). The sibling dormant sets on the casting side are [cas-03-evidence.md](cas-03-evidence.md), item 28.
