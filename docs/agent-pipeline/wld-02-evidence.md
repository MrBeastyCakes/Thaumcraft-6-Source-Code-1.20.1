## Reference behavior (source-derived)

### A. The sapling block

1. **One block class covers both species; the species is the block identity and the only state is a two-value stage bit.** `BlockSaplingTC` extends the vanilla bush base and implements the growable interface; it carries a single integer stage property over zero and one, a bush-sized collision box, a plant sound type, and the mod's creative tab, and it stores the stage in the meta bit three (`common/blocks/world/plants/BlockSaplingTC.java:25-36`, `:38-48`, `:143-151`, `:157-160`). Both species register this same class — `sapling_greatwood` and `sapling_silverwood` (`common/config/ConfigBlocks.java:222-223`) — against the shared API fields (`api/blocks/BlocksTC.java:20-21`), both join the tree-sapling ore dictionary (`api/OreDictionaryEntries.java:34-35`), and both appear by name in the language file (`assets/thaumcraft/lang/en_us.lang:254-255`). The two species are distinguished nowhere else: no per-species growth rate, biome check, or cost exists, only the branch in the tree attempt (finding 4).

2. **Time growth: server-side random ticks, full light above, and a one-in-seven roll — and a hidden second stage before any tree.** The tick refuses the client side, defers to the inherited bush tick, then requires light from the block above of at least nine plus a one-in-seven random roll before it calls the growth step (`common/blocks/world/plants/BlockSaplingTC.java:50-57`). The growth step advances the stage to one on the first success and attempts the tree only on the second (`:59-66`), so even the smallest time-grown tree needs two successful rolls, and a stage flip is invisible — both stages render from the same model — so the checklist measures outcomes, never stages (T2). A failed tree attempt leaves the sapling at stage one and it retries on later rolls; nothing is announced either way.

3. **Bonemeal: the block always offers to grow, and a quarter-chance gate decides whether an application does anything.** The growable test answers true unconditionally, the bonemeal test is a roll under one quarter, and the interface's grown overload delegates to the same growth step (`common/blocks/world/plants/BlockSaplingTC.java:131-141`) — so roughly one application in four advances a sapling, and a tree from stage zero averages around eight applications before failure rolls are counted. Nothing else gates bonemeal: the block consults no biome, research, aura, or daylight state, and the class itself plays no sound and spawns no particle on any outcome. The consumable's visible sparkle and its consumption belong to the vanilla application path outside this tree; the checklist records whether a refused application still consumes the item, and how the refusal reads (T2).

4. **The greatwood needs a two-by-two; a lone greatwood sapling can never grow, and the refusal is silent.** The tree attempt first consults the Forge terrain-generation veto and abandons when it refuses (`common/blocks/world/plants/BlockSaplingTC.java:68-71`). For a greatwood sapling it scans the four two-by-two windows that touch the clicked block and matches only when all four positions hold the greatwood sapling (`:72-87`, the window test `:118-125`); with no match it returns without placing anything, without a message, a sound, or a particle (`:92-94`). A silverwood sapling takes the other branch — a single-column tree, no second sapling needed (finding 6). When a window matches, the four saplings are cleared before generation and a failed generator call restores the clicked block's state into all four positions (`:95-115`) — a wrinkle the port should decide deliberately, because a failure can rewrite a neighbour's stage. The flow is the port's defect surface: the reference constructs its generators in code at this call site (`:81`, `:89`), so the port's "features resolve to `null`" is a missing registration in the port's data scheme, not a reference behavior.

5. **The block's checks are exactly these and no others: time, bonemeal, light, soil, space.** The block inherits its planting rules from the vanilla bush base (soil under the block) and its drop is itself with damage figure zero (`common/blocks/world/plants/BlockSaplingTC.java:127-129`). The growth step never consults the biome, so both species grow from saplings anywhere they can be planted; the magical-forest coupling of section D is worldgen-only. The tree attempt's space and soil checks live inside the two generators (findings 6 and 7), not in the block.

### B. The tree generators

6. **The greatwood generator is a hand-written big-tree build: a clearance-limited height between eleven and twenty-one, a two-by-two trunk, and two canopy passes.** The class extends the vanilla abstract-tree base with attenuation, branch, width, leaf-density, trunk-size, height-limit, and leaf-distance figures all hard-coded, and a spider flag (`common/world/objects/WorldGenGreatwoodTrees.java:42-57`). The height limit starts as eleven plus zero-to-ten random and is then overwritten by the measured clearance when the location tests find a lower ceiling (`:370-372`). Location testing checks each of the trunk footprint's four columns: soil that sustains a vanilla sapling, and a vertical line of replaceable blocks whose clearance, if under six, refuses the tree outright — otherwise the clearance becomes the height limit (`:292-333`, `:335-358`, `:375-382`). The build then runs twice: once from the base and once more with a wider canopy width from the first trunk's top, so the silhouette is a stacked double crown (`:383`, `:384-395`). Leaf nodes are discs of radius two to three laid on branch lines, placed only into air or existing greatwood leaves that allow replacement (`:59-119`, `:121-150`, `:152-180`); branches are placed only for nodes high enough in the tree (`:239-241`, `:276-290`); the trunk is the two-by-two column set (`:243-274`). Trees grown with the spider flag additionally get a cave-spider spawner under the trunk, up to fifty web attempts on air cells touching greatwood leaves or logs, and a chest of dungeon loot beside it (`:396-415`) — and that variant is reachable from worldgen only, because the sapling path passes the flag false while both worldgen paths roll one in eight (finding 15).

7. **The silverwood generator is a different, single-column build: a space scan, a cross-based trunk with arms and stubs, and a probabilistic leaf ball.** The constructor takes notify, a minimum height, and a random range, and derives its worldgen flag from the notify flag being off — which is what later controls the shimmerleaf gift (`common/world/objects/WorldGenSilverwoodTrees.java:24-30`). Height is seven plus zero-to-three through the sapling and mod-generator callers (`:32-33`; `common/blocks/world/plants/BlockSaplingTC.java:89`; `common/world/ThaumcraftWorldGenerator.java:254`) and eight plus zero-to-four through the biome's feature list (finding 14). It first scans a profile of increasing width over the full height and refuses if anything solid interrupts it, then requires soil that sustains a vanilla sapling (`common/world/objects/WorldGenSilverwoodTrees.java:41-63`, `:67-71`). The leaves are placed cell by cell over a five-block radius around the crown, each cell only when its squared distance from a clamped core sits under a random ten-to-seventeen threshold and the target allows leaf replacement (`:72-87`). The trunk is a five-wide column through the height with a centre cap one block higher, base diagonals, four arm stubs, stump-like stubs at the base and below it, and a second arm set four levels down with an additional one-in-three chance on some diagonals (`:88-144`). Every placement goes through the class's own override, which refuses any target that is not air, leaves, or replaceable — so the tree cannot overwrite solid builds (`:154-159`). The shimmerleaf run happens only when the worldgen flag is set (`:145-148`): worldgen silverwoods seed shimmerleaf under themselves, **sapling-grown silverwoods do not** — a parity-relevant asymmetry the port must keep (T3, T5).

8. **The flower helper both the silverwood gift and the cinderpearl path use: eighteen attempts in a small cloud, air above grass or sand only.** Its generator holds a plant block and meta, and each attempt picks a position within eight blocks horizontally and four vertically of the origin, placing the plant only where the target is air and the block below is grass or sand (`common/world/objects/WorldGenCustomFlowers.java:15-18`, `:20-31`). The silverwood passes the shimmerleaf block (`common/world/objects/WorldGenSilverwoodTrees.java:146-147`); the mod's per-chunk pass passes cinderpearl (finding 15). The two plants themselves glow — shimmerleaf at a light of four tenths with drifting motes, cinderpearl at a half with smoke and flame (`common/blocks/world/plants/BlockPlantShimmerleaf.java:19-27`, `:39-46`; `common/blocks/world/plants/BlockPlantCinderpearl.java:19-27`, `:39-46`) — and their names sit with the other plants in the language file (`assets/thaumcraft/lang/en_us.lang:281-282`). The biome's own decoration also seeds a third plant, the vishroom, beside wood (finding 14).

### C. The leaf economy and the aura nudge

9. **Leaf states split the two species: greatwood leaves enter the world armed for decay, silverwood leaves do not, and hand placement disarms both.** The leaf block's default state has both decay bits set — the decayable bit and the decay-check bit (`common/blocks/world/plants/BlockLeavesTC.java:36-41`) — and the greatwood generator places exactly that default state (`common/world/objects/WorldGenGreatwoodTrees.java:139-141`), while the silverwood generator places meta one, which the block's meta mapping resolves to decayable but **without** the decay check (`common/world/objects/WorldGenSilverwoodTrees.java:83`; `common/blocks/world/plants/BlockLeavesTC.java:96-109`). A player-placed leaf of either species is forced to non-decaying on placement (`:60-65`). The consequence a port must preserve: natural greatwood canopies run the inherited decay machinery; natural silverwood canopies do not self-decay; and breaking any modded log arms a nine-by-nine box of leaves around it through the log's own break hook (`common/blocks/world/plants/BlockLogsTC.java:79-90`). The checklist records how each canopy actually behaves (T4).

10. **Sapling drops are renewable but slow: a divisor of seventy-five against the inherited twenty, and a quicksilver roll on silverwood leaves.** The leaf class overrides the inherited sapling-drop divisor to seventy-five (`common/blocks/world/plants/BlockLeavesTC.java:111-113`) and routes the dropped item to the correct species sapling — silverwood leaves to the silverwood sapling, everything else to the greatwood sapling (`:121-123`). The inherited vanilla 1.12.2 drop contract (read outside this tree for this note) rolls the sapling on one in that divisor, reduces the divisor by a doubled amount per fortune level — four, then eight, then sixteen — with a floor of ten, and hands the apple-style hook a separate two-hundred-based figure reduced by ten, doubled per fortune level — twenty, forty, eighty — with a floor of forty; the class's override of that hook takes three quarters of the handed figure, truncating, and rolls one in the result for a quicksilver nugget on silverwood leaves only (`:115-119`; the nugget's name `assets/thaumcraft/lang/en_us.lang:54`). So at no fortune a decayed silverwood leaf yields a sapling at roughly one in seventy-five and a quicksilver drop at roughly one in a hundred and fifty, while a greatwood leaf yields only the rarer sapling. Shears return the leaf block itself, and silk touch returns the leaf block too (`common/blocks/world/plants/BlockLeavesTC.java:85-87`, `:129-132`), so a player can both farm and move the canopy. This is the renewability claim of the workboard item: both saplings recur from standing canopies, but the rates are the class's own hard-coded figures and nothing accelerates them.

11. **The wood side: a glowing silverwood log, decay arming on every break, and ordinary wood recipes.** The silverwood log emits light five — the pale, soft wood of the player text, its glow a code-side figure — where the greatwood log does not (`common/blocks/world/plants/BlockLogsTC.java:39-41`; the silverwood page text `assets/thaumcraft/lang/en_us.lang:1274-1275`), and every modded log's break hook arms the leaves around it (finding 9). Both logs carry axe-harvest hardness and axis-state placement like ordinary logs (`common/blocks/world/plants/BlockLogsTC.java:26-37`, `:58-65`), both satisfy leaf support and the wood test for other systems (`:71-77`), both are planks sources and smelt into charcoal (`common/config/ConfigRecipes.java:445-446`, `:490-492`), and both join the log and leaf ore dictionary entries (`api/OreDictionaryEntries.java:28-29`, `:36-37`). Aspect attribution — greatwood carrying life, silverwood carrying aura, and the saplings' split figures — is registered alongside and is [fnd-04-evidence.md](fnd-04-evidence.md)'s surface (`common/config/ConfigAspects.java:499-504`).

12. **The only aura interaction in the tree lane is a slow positive nudge from silverwood leaves; growth itself costs nothing.** On its random ticks, a silverwood leaf whose decayable bit is set and whose chunk's vis sits under the chunk's aura base adds a hundredth of a vis point to the chunk (`common/blocks/world/plants/BlockLeavesTC.java:89-94`) — the exact mechanism behind the player text's claim that naturally grown silverwoods slowly replenish the aura around them (`assets/thaumcraft/lang/en_us.lang:1274`), and the one place this lane touches the substrate of [wld-01-evidence.md](wld-01-evidence.md). Greatwood leaves carry no such hook. Nothing in the sapling block or either generator reads or drains the aura, so tree growth is free of any vis or research price; the aura generator that runs on the same world-gen callback is independent of it (finding 15; [wld-01-evidence.md](wld-01-evidence.md) findings 8-10).

### D. Biome coupling and the worldgen path

13. **The magical forest is a temperature-and-rainfall-tagged biome added to two climate bands at a configurable weight.** It is constructed with base height two tenths, variation three tenths, temperature eight tenths, and rainfall four tenths, then registered and given the magical and forest dictionary types (`Registrar.java:108-114`; `common/world/biomes/BiomeHandler.java:107`). When the magical-forest flag is on it is added once to the warm band and once to the cool band at the configured weight (`Registrar.java:115-117`), default five on both (`common/config/ModConfig.java:377-378`) — this weight is the only knob for how often the biome appears, and the comments say higher values suit biome-heavy modpacks. Its tree list is drafted inside the biome (finding 14), and its player-facing identity is the two tree pages of the plant research (`assets/thaumcraft/research/basics.json:92-103`; the page texts `assets/thaumcraft/lang/en_us.lang:1272-1278`).

14. **The biome's own feature list mixes the two magical species with a vanilla-blocked big filler tree.** Its random tree feature is one in eighteen silverwood (through the biome's own caller, eight plus zero-to-four levels), else one in twelve greatwood with the spider roll, else the big filler tree (`common/world/biomes/BiomeGenMagicalForest.java:62-64`). The filler tree is a vanilla-style big-tree generator seeding **vanilla** logs and leaves, its leaves placed with the decay check cleared (`common/world/objects/WorldGenBigMagicTree.java:39-49`, `:123-127`, `:175-185`, `:219-236`) — so the biome's third tree is an ordinary giant tree, and a port that maps it to a modded species changes what a magical forest yields. Decoration counts per chunk are trees two, flowers ten, grass twelve, waterlilies six, mushrooms six, and the biome's own decoration converts ambient grass, drops mossy blobs and giant mushrooms, and seeds vishrooms next to wood (`common/world/biomes/BiomeGenMagicalForest.java:55-59`, `:66-68`, `:84-123`, `:125-139`). Client colour, recorded here as a parity fact with its render plumbing in the CLI lanes: silverwood leaves are left untinted while greatwood leaves take the biome foliage tint (`client/ColorHandler.java:68-77`).

15. **The mod's own generator is registered once and runs per chunk through gates now familiar from the aura lane: dimension blacklist, config flag, flat-world refusal, and the generation-or-regeneration switch.** Registration sits in the pre-initialization block with weight zero (`proxies/CommonProxy.java:61-63`), and the per-chunk callback runs the whole feature pass and then the aura generator on the provided chunk (`common/world/ThaumcraftWorldGenerator.java:48-51`). The feature pass is admitted only when the dimension is not blacklisted, the tree flag is on, the world type is not flat, and the chunk is new or the tree-regeneration flag is on (`:215-220`); that gate family — dimension blacklist for the pass, biome blacklist per chunk, and the separate ore gate — is the same blacklist pair whose non-consultation by the aura path [wld-01-evidence.md](wld-01-evidence.md) finding 10 records. Inside the pass, a biome-blacklisted chunk stops outright (`:106-110`), then rolls silverwood at one in eighty, greatwood at one in twenty-five, and a cinderpearl seeding on hot sand at one in thirty (`:111-122`). Both tree placements pick a centre within four blocks of the chunk centre, resolve the precipitation height, and then test the biome: greatwood rolls against the biome's support figure (`:235-245`), while silverwood passes on **half** the support figure, or on any magical-dictionary biome other than the mod's own magical forest, or on the two literal vanilla biome ids eighteen and twenty-eight — the forest-hills and birch-forest-hills slots (`:247-258`). The same file also carries the structure pass — a mound and a lesser cultist portal, gated by the structure flag — which is `WLD-04`'s surface and is not derived here (`:71-94`). The nether hook is an empty body with an unused local (`:226-228`).

16. **The support lookup that both tree rules read is a dictionary walk that returns the first supporting entry, not an average.** The greatwood support figure walks the biome's dictionary types and returns the chance of the first entry that flags greatwood support, defaulting to zero when none does (`common/world/biomes/BiomeHandler.java:59-70`), while the aura modifier for the same biome averages its entries (`:32-46`) — the two lookups in this lane genuinely differ. The registered figures carry support on the magical, forest, lush, coniferous, savanna, plains, and swamp types — full strength on magical and forest, a half on lush, a fifth on the rest (`:104-137`; entries per type `:28-30`), so an ordinary forest is as strong a greatwood region as the mod's own forest, and the silverwood rule of finding 15 then halves that. Which entry wins for a biome carrying two supporting types is not established by this read (unverified list).

17. **The regeneration path re-runs the same pass on queue-marked chunks.** A loaded chunk without the world-generation marker is queued when any regeneration flag is on (`common/lib/events/ChunkEvents.java:78-89`), and the paced regeneration tick drains that queue with the generator call set to the non-new flag (`common/lib/events/ServerEvents.java:178-203`, the call `:195`) — so with the tree-regeneration flag on, a re-run chunk re-rolls the vegetation pass — the same queue `WLD-01` finding 14 describes for the aura side, where the re-run notably skips the aura and here it re-rolls the vegetation. The trees placed by the first run are not removed by the second; the observation is whether any duplicate or topology artifacts appear (T7).

### E. Config, secondary sources, and the wrinkles a port must decide

18. **The config surface for this lane is four world flags and one weight, and unlike the aura lane both flags here have live readers.** The tree flag (default true) gates the vegetation pass (`common/config/ModConfig.java:354`, `:387`; reader `common/world/ThaumcraftWorldGenerator.java:218`), the tree-regeneration flag (default false) gates the re-run of that pass on queued chunks (`common/config/ModConfig.java:363`, `:395`; reader `common/world/ThaumcraftWorldGenerator.java:218`), and the magical-forest flag and weight control the biome (finding 13) (`common/config/ModConfig.java:337-341`, `:377-378`). No per-tree rate, height, drop figure, or shimmerleaf toggle exists: every roll and divisor in this note is hard-coded in its class.

19. **Secondary sapling sources exist but are other lanes' surfaces.** Saplings also appear as Pech barter outputs — the greatwood sapling in the second value tier and the silverwood sapling in the fifth — in the trade tables (`common/config/ConfigEntities.java:144`, `:153`), drawn by the barter container's payout loop (`common/container/ContainerPech.java:74-123`); the creature itself is `WLD-05`'s, cited here only to show the second acquisition path to a sapling exists beside leaf decay. The research-side discovery of the plants is the scanning lane's (`common/config/ConfigResearch.java:193-197`, `RSR-01`), and the plants' crafting and alchemy consumers are the crafting lanes' surfaces.

20. **Wrinkles to decide rather than copy blindly.** (a) The spider greatwood is worldgen-only: the sapling path passes the flag false (`common/blocks/world/plants/BlockSaplingTC.java:81`) while both worldgen paths roll it (`common/world/ThaumcraftWorldGenerator.java:241`; `common/world/biomes/BiomeGenMagicalForest.java:63`) — a sapling player must never meet it, and the port must keep that split. (b) Silverwood heights differ by caller — seven plus zero-to-three from saplings and from the mod's generator, eight plus zero-to-four from the biome's feature list (finding 7) — a variance a port that collapses callers will visibly lose. (c) A failed greatwood attempt rewrites all four matched saplings to the clicked block's state (finding 4). (d) The stage flip is unobservable from the model; the checklist measures trees, never stages (finding 2). (e) The reference ships no resource-tree worldgen and no `init/` package for this lane — the whole path is code — so the port's data-driven roots are its own schema and carry no reference counterpart to diff against (port-gap row).

## Multiplayer and divergence classes

21. **Everything in this lane is server-side and nothing is networked beyond ordinary block updates.** The sapling's growth tick refuses a client, both generators run inside chunk generation or the tree tick on the logical server, and no class in this lane sends or registers a packet; clients learn of a tree through block updates and of the leaf nudge only through the aura readout packet while a reading tool is held ([wld-01-evidence.md](wld-01-evidence.md) findings 15-16). Two clients cannot disagree about a grown tree; they can disagree only about when their readouts sampled the nudge (T8).

22. **Determinism and the reload probes.** The greatwood generator derives its own random by drawing a long from the caller's stream and reseeding (`common/world/objects/WorldGenGreatwoodTrees.java:363-372`) while the silverwood generator consumes the shared random directly (`common/world/objects/WorldGenSilverwoodTrees.java:32-33`) — so worldgen trees should reproduce under a recorded seed while sapling growth from bonemeal is not reproducible by hand; the checklist pins seeds and coordinates instead (T1, T5). The stage bit is block metadata, so a sapling mid-way through its two stages survives a reload; a canopy mid-decay and a tree mid-generation are the T4 and T7 reload observations.
