## Reference behavior (source-derived)

### A. The payload and the backlog it answers to

1. **The reference tree ships 1,520 files under `assets/thaumcraft` — and a scripted walk of the whole `src/main/resources` tree counts 1,537 resource files total, matching the number `REF-0001` records for its jar comparison.** The breakdown, from the walk: 504 JSON, 767 PNG, 111 OGG, 81 `.mcmeta`, 27 OBJ, 6 MTL, 9 `.lang`, 7 JPG, 3 `.frag`, 2 `.vert`, plus a Markdown file, a plain-text file, and a licence file; the six remaining resources are five at the root (`changelog.txt`, `mcmod.info`, `pack.mcmeta`, `dependencies.info`, `TCLogo.png`) and one under `META-INF/` (an access-transformer config). By directory: 219 blockstate files; 127 files under `models/block` (119 JSON plus four OBJ/MTL pairs for the charger, golem builder, pillars, and thaumatorium), 157 under `models/item` (155 JSON plus the scanner OBJ/MTL pair), and 23 under `models/obj` (22 OBJ plus one MTL); nine files under `research` (eight research JSONs — seven category definitions plus the scans table — and an example); five shader sources under `shader`; two loot-table files; eleven language-directory entries (nine `.lang` files, a licence, and a readme); 111 sound files plus `sounds.json`; and the fourteen texture directories detailed in finding 10. An eleven-file overlay under `assets/minecraft` (four vanilla post-shader descriptors and seven shader programs) replaces vanilla shader assets and is the tree's only write into another namespace. The point of the census is arithmetic for the port: the "no missing assets" acceptance is a claim about roughly fifteen hundred files, and the sweeps below (findings 4, 6, 14, 16) are the mechanical way to hold it.

2. **`TEXTURETODO.md` is the port's own backlog document, not a reference-tree file — the reference tree carries no file by that name — and its contents are structured as four asset classes plus a fix guide.** A name search (`find` for any case variant of "texturetodo") and a content search across the decompiled tree return nothing; the file lives at the port repository root (present in this worktree's checkout) and titles itself as the list of placeholder textures and missing assets that need creating or sourcing. Its structure: a first table classifies missing *item* textures into three priorities — high (nine commonly used items: the thaumometer, both phial states, the two research-notes items, both label states, one golem seal, and the base blank seal), medium (five: a bauble charm, the pure-fluid bucket, a curio base, a second golem-brain variant, and a master caster), and low (twelve celestial-notes variants: eight moon phases and four star patterns); a second table lists four item models still painting with a generic placeholder; a third lists seven *block* models whose textures are substitutes rather than the dedicated art, including three effect blocks the document itself says should be invisible, a reservoir, a scrubber, a focal manipulator, and a pedestal doorway; a fourth section asks whether seven research-browser category icons resolve at a `gui/category` path; a fifth asks that entity textures be verified for the golem material variants, the wisp, the pech, the cultist variants, and the eldritch variants; a fix guide offers an extraction route from the original jar, a redraw route, and a fallback route; and a statistics footer counts 212 item textures and 250 block textures in the port, with roughly thirty item textures missing, four placeholders, and seven substitute block textures, followed by a quick-fixes note and a January 2026 date. Read as rank-4 evidence (the workboard's own primary area names it), this is the port's statement of what its asset layer lacks — the reference-side answer to each row is finding 3.

3. **Most of the port's "missing" names map to reference files under different names or paths, and a bounded set has no reference counterpart at all.** A scripted name search across the reference payload, row by row against finding 2's lists: the base blank seal exists as `textures/items/seals/seal_blank.png` (the port's path guesses `seal_blank.png` at the items root); the same directory ships the seal family under `seal_` plus purpose names, so the port's "provide" seal is the reference's provider seal (one letter); the golem-brain variant exists as `mind_biothaumic.png` and `mind_clockwork.png` (animated, with metadata); the caster texture exists as an armour-layer file under `textures/entity/armor/`, not under items; the celestial set exists with unsuffixed names — `moon1.png` through `moon8.png` and `stars1.png` through `stars4.png`, plus a sun and a sheet, fourteen files — rather than the port's `celestial/moon_1.png` spelling; the phial pair exists as `phial.png` plus an animated overlay (`phial_overlay.png` with metadata) rather than empty/filled names; the label pair exists as `label.png` plus `label_overlay.png`; the four placeholder'd module and grapple-gun items exist as `module_aggression.png`, `module_vision.png`, `grapple_gun_spool.png`, and `grapple_gun_tip.png`; the substitute block textures the port lists exist for the *reference's* blocks: the workbench side/top textures, the advanced and basic alchemical metal textures, and the ancient stone texture are all present, the reference's condenser art (`textures/blocks/condenser.png`) is the port's scrubber counterpart, the reference's wand-workbench side/top art is the focal-manipulator counterpart, and the reference's `eldritch_door` texture — used by its doorway block's own blockstate — is the doorway counterpart. Genuinely absent from the reference payload: `thaumometer.png` (the reference's thaumometer item art is the scanner pair — `textures/items/scanner.png` and `textures/items/scanscreen.png`, bound by the item's state file, finding 5), `research_notes.png`/`research_complete.png` (the reference registers no research-notes item and ships no such texture; the nearest item art is the scribing tools), `primal_charm.png` (the reference's charms are undying, verdant, and voidseer — three items, no primal charm), `curio_common.png` (the reference's curio art is per-type: six `curio_*.png` files plus a curiosity band pair), `placeholder.png` (port-only), `bucket_pure.png` (absent from the reference too — its own item model references it anyway, finding 14), and a root-level `empty.png` (the reference's `empty.png` is under `textures/blocks/`, and the reference's effect blocks do not bind it — they use an empty *model*, finding 15). What a port must replace versus keep, stated once: **keep** everything finding 1 counts, with the renames above; **author** the genuinely absent art (the port's own placeholder set) or adopt the reference's substitutes where the port invented a name; **copy the reference's naming** for every file the port's models already point at under a wrong name; and **do not copy** the dead files finding 16 lists.

4. **The reference tree's own self-consistency is near-perfect, and this note's mechanical sweeps are the proof a port can re-run.** Three scripted sweeps over the reference payload: (a) every blockstate model reference resolves — 729 into `models/block`, one into `models/item` (the crimson cult banner state file, whose model lives in the item folder), 25 into OBJ files that exist, zero unresolved; (b) every JSON model's `parent` resolves — 38 thaumcraft parents and 173 vanilla parents, zero missing; (c) every thaumcraft texture a JSON model binds resolves except the single pure-bucket miss of finding 14 — 473 references, one miss. The same sweeps over the Java sources (finding 14) find the remaining holes. This is the artifact a port-side asset checklist should imitate: name checks are cheap, and the reference's own holes are exactly three classes — one item texture, three dead beam textures, and orphaned metadata files (finding 16).

### B. The model layer

5. **Blocks and items model in JSON with a Forge marker convention, and six blockstate files plus one item state file drive OBJ models instead — including the thaumometer, whose state file is the item's whole model.** The blockstate format in this tree is Forge's marked form: each file has a marker key and a defaults block carrying the model name and transform, with variant lists underneath (`assets/thaumcraft/blockstates/alembic.json` is the minimal example); the state files reference models by name with the folder implied — the walk in finding 4 shows every reference resolving into `models/block` except the banner exception. Seven state files reference OBJ models directly — the six block device states (the arcane workbench charger, the golem builder, the three pillar variants, and the thaumatorium; twenty-four references between their variants) and, the surprise, `assets/thaumcraft/blockstates/thaumometer.json`, which binds the scanner OBJ with two named textures (a body material and a pane material) plus a flipped-V custom flag and a full per-display transform set: first-person, both third-person poses, GUI, ground, and fixed. So the reference's thaumometer item model is not a missing file — it is an OBJ-driven item state file, and a port that "creates a thaumometer model" from scratch misses that the art files are the scanner pair (finding 3). The item folder's 155 JSON models cover the remainder, resolved by registry name with variant suffixes (finding 7); the `models/obj` folder's 22 OBJs are the code-loaded set of finding 9.

6. **One model in the whole payload binds a texture the tree does not ship — and both bucket item models describe items the code never registers.** The file `assets/thaumcraft/models/item/bucket_pure.json` is a generated-item wrapper whose single texture reference, `thaumcraft:items/bucket_pure`, resolves to no file; the items folder ships only the sibling bucket texture, and no pure-bucket texture exists anywhere in the payload. The pair's context: the tree registers no bucket items at all — its two fluids ride Forge's universal bucket (`Thaumcraft.java:69`; `common/config/ConfigBlocks.java:352`, `:355`) — so both bucket item models are files for a cut item set, and the pure one carries the payload's only model-to-texture miss (finding 4's sweep). A port that copies the payload faithfully copies this hole — and should decide, as a recorded adaptation rather than as parity, whether the pure bucket model is worth authoring art for or deleting with its dead sibling.

7. **Item models register through one loop with four resolution branches, and block items get a single inventory model from the client proxy.** The item side: every registered item implementing the mod's item interface lands in one list, and the client model pass walks that list (`common/config/ConfigItems.java:330-331`) with four branches (`:336-354`): a custom mesh definition plus per-variant models for items that declare one; a seal special case that appends the variant name to the registry name; the plain single-model registration for non-subtyped items (`:349`); and the per-variant registration for subtyped items (`:353`). The base class supplies the defaults — no custom mesh, and a model location of namespace plus base name, with the variant appended when it is not the base (`common/items/ItemTCBase.java:70-79`) — a default the hand-built armour pieces keep by stubbing the mesh override with a null return (finding 24). The block side: block items are registered with their registry name plus the inventory variant (`proxies/ClientProxy.java:82`), while the block models themselves are routed in the block-registration event (`Registrar.java:53` calling `proxies/ProxyBlock.java:38`): slab variants by half and variant, banners and nitors to shared inventory models, mirrors with an on/off item-variant pair, the three fluid blocks to mesh definitions and state mappers that point at single fluid models, and the shard ores to a state mapper over the crystal model that the bake hook then swaps (finding 9). The jar items add a fill-level override chain: the jar item model is an override list keyed on a fill property with five entries mapping fill levels zero through four to the block-side jar models including the four empty-to-full intermediates (`assets/thaumcraft/models/item/jar_normal.json`, mirrored for the void jar), which is the mechanism the port must reproduce if jar inventory icons are to show fill — and one dead corner: the proxy declares two jar model arrays and initializes them in its static block, but nothing ever writes or reads them (`proxies/ProxyBlock.java:31-32`, `:105-106`) — a leftover of the same device whose live path is the override chain.

8. **The hand-built model classes are 28 files in three packages, and two of them are dead.** The block-model package holds ten classes — banner, bellows, two bore shells (base and emit), brain, centrifuge, jar, research table, tube valve, and the bore piece — of which `client/renderers/models/block/ModelBore.java` and `client/renderers/models/block/ModelBoreEmit.java` have zero references anywhere in the tree (a scripted reference count): the live bore shell is the emit-less base variant used by three tile renderers (alembic, bellows, pattern crafter), which is the model-side echo of the dead-field finding [aut-03-evidence.md](aut-03-evidence.md) records for the bore entity. The entity-model package holds twelve classes covering the arcane bore, the turret crossbow, the eldritch crab, the eldritch golem, the eldritch guardian (shared by the warden), the fire bat (shared by the spell bat), the grappler (shared by the grapple and the focus mine), the pech, the taintacle pair, and the taint seed pair — the seed and taintacle packages each ship a base renderer-model class plus the concrete model, an internal split with no other users. The gear package holds five armour models on one base class. The shared cube model completes the set. Every class above is referenced exactly where the mapping says; the two dead bore classes are the only unused ones.

9. **The golem is the tree's OBJ showcase: its parts are registered as object-model-plus-texture pairs in one registry block, and its renderer loads a base OBJ and draws parts per attach point.** The golem property registry registers, in one contiguous block, six materials (`common/golems/GolemProperties.java:200-205`, one `textures/entity/golems/mat_*` texture each), then five heads, five arms, four legs, and four addons (`:206-223`) — each of those carrying an OBJ model location under `models/obj` plus one or two texture locations under `textures/misc/golem` and `textures/entity/golems`. The no-addon entry is the one registration in the whole payload that names a missing texture file (the file `textures/blocks/blank.png`, named at `common/golems/GolemProperties.java:220`; it exists nowhere in the tree) — the entry has no part model attached, so a capture is the arbiter of whether it ever binds (T8). The renderer loads the base OBJ at construction and caches part models keyed by attach point (`common/golems/client/RenderThaumcraftGolem.java:54-59`), and the registry owns the variant table. The port-relevant statement: golem appearance is data, not code — the registry block is the single table a port must mirror, and the OBJ-plus-two-texture shape (a main part texture and, for several parts, a second overlay texture from the entity folder) is the compositing model to copy.

### C. The texture layer

10. **The payload's 767 PNGs live in fourteen texture directories, split between gameplay art and effect art, with 81 animation descriptors riding along.** The census, from the scripted walk: `textures/blocks` holds 209 PNG plus 11 `.mcmeta`; `textures/items` holds 182 plus 16, with two subdirectories — `celestial` (14 files, the notes variants of finding 3) and `seals` (17 plus 16, the golem seal family); `textures/models` holds 68 plus 32 (the largest descriptor count — the frame sets of finding 13); `textures/research` holds 46 (category icons, page art, knowledge icons, entity research icons); `textures/misc` holds 26 plus 6 with a `golem` subdirectory of 37 (the golem part and trait-tag textures); `textures/gui` holds 34 plus seven JPG research backgrounds; `textures/entity` holds 23 at the root with `armor` (20) and `golems` (13) underneath; `textures/foci` holds 39 (the focus part and modifier icons, whose semantics are [cas-01-evidence.md](cas-01-evidence.md)'s and [cas-02-evidence.md](cas-02-evidence.md)'s); and `textures/aspects` holds 39 (the aspect icons whose attribution is [fnd-04-evidence.md](fnd-04-evidence.md)'s). The `.mcmeta` distribution matters for a port: animation is concentrated in blocks (11), items and seals (32), models (32), and miscellaneous (6) — the two biggest descriptor clusters are the animated frame sets and the animated items.

11. **Two code hooks extend the JSON layer: a stitch pass that registers six extra sprites and a bake pass that swaps the shard-ore model for a code-built one.** The stitch hook subscribes to the pre-stitch event and registers six sprites into the block atlas — the research quill, the crystal block texture, and four taint-growth frames (`client/lib/events/RenderEventHandler.java:754-763`) — which is the list to check first when a port sees missing sprites after a texture rename, because these six are referenced by code, not by any model file. The bake hook runs on the model bake event: it pulls the crystal sprite out of the block atlas, constructs the code-side crystal model with it, and writes that model back into the registry for every shard ore variant (`proxies/ProxyBlock.java:112-123`; the model class itself at `client/renderers/block/CrystalModel.java:34` loads the crystal OBJ and reports no overrides at `:164-165`). A third related hook is the client block-item mesh routing of finding 7; together these three are the whole of the code-side model/texture interplay.

12. **The GUI and research artwork a port must keep is wired from two unrelated classes.** The research category art is registered with the categories themselves: the seven category registrations carry each category's icon and background (`common/config/ConfigResearch.java:138-144`) — the basics category points at an item texture, the other six at `textures/research/cat_*.png`, and each pairs with one of the seven `textures/gui/gui_research_back_*.jpg` backgrounds — which answers the port backlog's question about category icon paths directly: the reference puts them at `research/cat_*`, and the binding code is the research config, not the browser ([cli-01-evidence.md](cli-01-evidence.md) item 9 owns the browser's drawing). The device screens' backgrounds are the `gui_*` textures listed in finding 10's census, consumed by [cli-01-evidence.md](cli-01-evidence.md)'s screens; this lane records only their names and counts.

13. **The effect-art file sets sit in `textures/models` and `textures/misc`, and the beam-texture set is split between live and dead files.** The models folder carries two fifteen-frame animation series — the hemisphere frames and the ripple frames, each with per-frame metadata — plus single effect sheets; the sonic effect binds the ripple series while the shield-rune effect binds both (`client/fx/other/FXSonic.java:71` binds the ripple frames; `client/fx/other/FXShieldRunes.java:62-63` binds the ripple and hemisphere frames), and both bind the shared hemisphere OBJ (`client/fx/other/FXSonic.java:103` and `client/fx/other/FXShieldRunes.java:130`; the frame stepping is [cli-02-evidence.md](cli-02-evidence.md) item 9's). The misc folder carries the particle atlas with its descriptor, the three live beam textures the [cli-02-evidence.md](cli-02-evidence.md) beams bind, and the node and particle-field sheets. The dead half: the two retired wand-era beam classes bind three beam textures that do not exist anywhere in the payload (`textures/misc/beam.png`, `beam2.png`, `beam3.png`, from `client/fx/beams/FXBeamBore.java:68-71` and `client/fx/beams/FXBeamWand.java:71-74`) — the classes are dead by [cli-02-evidence.md](cli-02-evidence.md) finding 6 and their art was evidently cut with them, so a port that resurrects either class resurrects a missing-texture bug.

14. **A whole-tree sweep for texture paths named in code finds the payload's real holes: two vanilla-namespace lookups that are not holes, three dead-class beam textures, and one registration pointing at a missing file.** The sweep reads 268 texture-path literals in the Java sources, 214 distinct; of the six that match no file, two resolve against the vanilla namespace and are correct as written — the arrow texture a dart renderer uses and the end-portal texture three classes reuse (`client/renderers/entity/projectile/RenderDart.java:103`, `client/fx/other/FXVoidStream.java:230`, `client/gui/GuiVoidSiphon.java:68`, `client/renderers/entity/RenderFluxRift.java:106` — all single-argument resource locations, so they name vanilla art). The remaining four are finding 13's three dead beam textures plus the golem registry's blank texture (finding 9). With finding 6's pure-bucket miss, the complete list of asset references the reference payload does not satisfy is: one model-bound item texture, three dead-code beam textures, one registry texture on a modelless entry, and the three orphan metadata files of finding 16. Everything else — hundreds of code-named textures and every live model binding — resolves.

15. **The effect blocks are invisible by data, and the reference says so in its own state files.** The three effect blocks' state files bind the tree's empty model — a zero-volume element model, `assets/thaumcraft/models/block/empty.json` — so their invisibility is a model property, not a missing texture: the port backlog's instinct to give them an empty texture is directionally right but the reference mechanism is the empty model, and the port's own substitute texture (`textures/blocks/empty.png`) exists in the reference as an ordinary block texture bound by the vis-crystal blockstates. The doorway block follows the same pattern with real art: `assets/thaumcraft/blockstates/stone_ancient_doorway.json` binds a cube-all model painted with the eldritch door texture. The lamps show the submodel mechanism the port backlog has no note for: three lamp state files bind a shared lamp model and add a stand submodel per facing with swapped side textures (`assets/thaumcraft/blockstates/lamp_arcane.json`). These three are the state-file shapes a port's block registry must support: empty model, cube-all with art, and base-plus-submodel with per-variant textures.

16. **The payload's dead and stray files are enumerate-able: three orphaned animation descriptors, one orphaned texture, three orphaned sounds, and the dead model classes and renderer pairs of findings 8 and 23.** The scripted stray-descriptor check finds three `.mcmeta` files whose same-named PNG is absent from the folder — one in `textures/misc` (a nodes descriptor, the file evidently renamed to a different sheet), one in `textures/models` (a ripple descriptor with the per-frame series alongside it), and one in `textures/models` for the scanner screen (whose PNG lives in the items folder with its own descriptor, so the models-folder copy is a duplicate) — 81 descriptors total, three stray. One texture has no referent of any kind: `textures/models/reservoir.png` names a device the reference does not implement (no reservoir block or class exists in the tree's Java). And the sound folder's three orphans are finding 17's. None of these break anything; all of them cost payload bytes and mislead a port that copies by directory.

### D. The sound layer

17. **sounds.json is five-category, sixty-five-key, one-hundred-eight-file, and subtitle-free — and three of the shipped files are unreferenced.** The scripted census of `assets/thaumcraft/sounds.json`: 65 top-level entries across the mod's five categories — 19 hostile, 18 master, 14 block, 11 ambient, and 3 player — expanding to 108 file references, with no entry carrying a subtitle and no entry streaming. The `sounds/` folder ships 111 OGG files: 108 are referenced by the JSON, and three — a roots set of three files — are referenced by nothing in the tree (the id already exists in the registry's neighbourhood but no key names them). A port that copies the folder copies the three orphans; one that derives the folder from the JSON drops them, and both should say which it did.

18. **The registry class is 65 static sound events plus four block sound types, and it contains the tree's one sound-id typo, which silences the runic shield charge sound.** The class declares 65 sound-event fields, registers each by identifier in one block, and builds four sound types — a flesh type, a crystal type, a jar type, and an urn type, each wiring one registered event into all five of its slots with a pitch pair (`common/lib/SoundsTC.java:11-75` fields, `:81-86` the type block, `:88-154` the registrations, `:156-161` the helper). The typo: the field and the registered id for the shield charge spell the suffix `charge` (`:131`), while the sounds.json key spells it `decharge` — so the registered charge event has no sounds.json entry (it resolves to silence in the reference), and the JSON's entry names no registered event. The shield effect sound, by contrast, is registered and has its JSON entry; but its field sits in the registry's never-triggered set — the scripted field-reference count finds six fields with no reference outside the registry class: the erase sound, the off-state device sound, the shield effect sound, the upgrade sound, the grind sound, and the urn-break field, and the last of those is consumed by the class's own urn sound type, leaving a five-id never-triggered set. The most-referenced events, for calibration: the zap, page, and clack sounds lead with eighteen, seventeen, and eleven call sites.

19. **The four block sound types are the sound layer's gameplay wiring, and the play-call surface is 125 files.** The material wiring is one line per block class: the jar type on the jar and mirror blocks (`common/blocks/essentia/BlockJar.java:47`, `:51`; `common/blocks/devices/BlockMirror.java:35`, `:44`), the crystal type on the crystal ore (`common/blocks/world/ore/BlockCrystal.java:58`, `:65`), the flesh type on the taint family and the flesh block (`common/blocks/misc/BlockFlesh.java:17`; `common/blocks/world/taint/BlockTaint.java:53`, `:58`; `common/blocks/world/taint/BlockTaintFibre.java:78`, `:85`; `common/blocks/world/taint/BlockTaintLog.java:32`, `:38`; `common/blocks/world/taint/BlockFluxGoo.java:37`, `:42`), and the urn type on the loot urn (`common/blocks/world/BlockLoot.java:32`). The event-driven side is bounded by count rather than by re-derivation: a scripted sweep finds play-call sites in 125 files — 115 under `common/` and 10 under `client/` — with the crafting devices, the wisp, the cultists, the bosses, and the gun and caster items among them (the infusion matrix plays its start, fail, and wand tones at `common/tiles/crafting/TileInfusionMatrix.java:351`, `:459`, `:695`, `:838`); the mechanics behind each trigger belong to the owning lane's note, and this lane records that the trigger surface exists at that scale and that the registry's never-triggered ids (finding 18) are the never-called subset.

20. **There are no music discs: nothing in the tree registers a record, plays a record, or ships disc art.** The sweeps agree — no play-record call site anywhere in the Java, no record item registration, and no disc or music files in the payload. A port that adds Thaumcraft-themed discs is adding content, not restoring it.

### E. The render layer

21. **Forty-three entity renderer registrations match forty-three registered entities one-to-one, and the registration block is the whole of the entity render wiring.** The entity registry registers its forty-three mod entities in one contiguous block of forty-three lines (`common/config/ConfigEntities.java:82-124`), each with tracking range, update interval, and spawn-egg colours; the renderer block registers forty-three renderers in one contiguous block of forty-three lines (`proxies/ProxyEntities.java:95-137`), constructed with the vanilla render manager and, where needed, a model instance and shadow size (the pech's shadow radius, the slime and taintacle scales, the guardian's model, and so on). A scripted class-by-class comparison finds an exact match in both directions: no registered entity lacks a renderer and no renderer registration lacks an entity. The wiring call sits in the client initialisation (`proxies/ClientProxy.java:44-45`), together with the tile pass below — and the "proxy split" the port row asks about is exactly this pair of proxy classes: the reference has **no** `RenderHandler` and no `RenderEntities` class; the entity renders live in `ProxyEntities.setupEntityRenderers` and the tile renders in `ProxyTESR.setupTESR`, both invoked once from the client proxy's init.

22. **The renderer-to-model split is by class, and it divides the mobs into a hand-modelled set, a vanilla-model set, and a code-drawn set.** Hand-modelled: the arcane bore (its own model class), the turret crossbow (a custom crossbow model; the advanced turret adds a code-loaded crossbow OBJ at `client/renderers/entity/construct/RenderTurretCrossbowAdvanced.java:114`), the eldritch crab, the eldritch golem, the eldritch guardian (shared by warden, differing only in scale per `proxies/ProxyEntities.java:116` and `:122`), the fire bat and spell bat (one model class, two renderers), the pech (with its held-item layer attached in the renderer; the folder's other layer class, the tainted-champion overlay, is attached from the champion-modifier code instead, `common/entities/monster/mods/ChampionModTainted.java:73-74`), the grapple and the focus mine (one grappler model class, two renderers), the taintacle (one class, three scale/tentacle-count presets at `proxies/ProxyEntities.java:110`, `:111`, `:119`), and the taint seed (one class, two presets at `proxies/ProxyEntities.java:108`, `:109`). Vanilla-modelled: the two zombie variants (biped and villager-shape models on the mod's own renderer classes, `RenderBrainyZombie`, `RenderInhabitedZombie`), the two cultist foot classes (biped), the taint crawler (the silverfish model), the thaumic slime (the vanilla slime model, sized), and the mind spider (the vanilla spider renderer subclass). Code-drawn, no model file: the wisp renderer, the taint swarm, the falling taint, the flux rift, the special item, and the projectile renderers. Two of these draw nothing by design — the taint swarm's renderer passes a null model and empties its render body (`client/renderers/entity/mob/RenderTaintSwarm.java:17`, `:20-21`), and the two focus projectiles are the no-op renderers [cli-02-evidence.md](cli-02-evidence.md) items 19-20 own — while the dart and orb projectiles draw their own quads or icons. The golem sits in its own client package under the golem code (finding 9). This split is the map a port needs: only the hand-modelled set requires model-class ports; the vanilla-modelled set requires finding each vanilla model's 1.20 counterpart; the code-drawn set requires render-method ports.

23. **Two renderer classes are orphans — registered to nothing and referenced by nothing — and this lane adds the second pair to the one [cli-02-evidence.md](cli-02-evidence.md) already records.** The scripted reference count finds zero references outside themselves for the homing-shard renderer and the rift-blast renderer, and their entity classes are referenced only from those same renderers: the homing-shard pair is the one [cli-02-evidence.md](cli-02-evidence.md) finding 7 already documents (its entity is absent from the registry and its beam never draws), and the rift-blast pair is the sibling case — a projectile entity class and a renderer class that nothing registers, nothing spawns, and nothing calls, so the rift-blast visual is not a live BETA26 surface either. The same sweep cross-validates finding 21: with the two orphan pairs excluded, every renderer class in the tree is registered.

24. **The tile pass binds twenty-three tile classes to twenty-two renderer classes, one instance serving two mirror tiles, and the item-render surfaces are the model overrides rather than item renderers.** The tile registration block binds twenty-three tile classes with twenty-three helper calls over twenty-two renderer classes (`proxies/ProxyTESR.java:53-78`; the mirror renderer instance is shared between the two mirror tiles at `:70-72`), against fifty-two tile classes in the tree — so twenty-three of fifty-two tiles have a special renderer and the rest render as JSON blocks. Representative bindings a port will exercise: the jar renderer (jar model plus a brain model for the brain jar), the chest renderer, the research-table and golem-builder surface renderers, the infusion matrix (the shared cube model), the tube family (three renderers over one valve model), and the pattern crafter. On the item side, the tree uses **no** tile-entity item renderer binding anywhere — the item-side visuals for devices are the model overrides and the mesh definitions: the fill-level override chain of finding 7 for jars, the on/off item variants for mirrors, and — a caution rather than a feature — the eleven armour classes' `getCustomMesh` overrides in `common/items/armor/` are null-returning interface stubs, not mesh definitions: every `getCustomMesh` body in the tree returns null, the only real custom mesh definitions are the three fluid items (`proxies/ProxyBlock.java:67`, `:79`, `:91`), the one call that would ever bind an item-side mesh for a registered item sits on a branch no item takes (`common/config/ConfigItems.java:338`, guarded by a non-null mesh test), and the custom-render helper the seal screen reuses (`client/lib/CustomRenderItem.java`, referenced only by that GUI class) routes no armour at all — the five hand-modelled armour pieces' in-world look comes from their armour-model overrides and the shared armour helper (`common/items/armor/ItemFortressArmor.java:69-76`), and the rest take their worn look from armour textures on the default model. A port that looks for item TESR bindings will find none, and should not invent them.

### F. Credit, delivery, and reload

25. **The tree's credit surface is three files and a licence, and none of them is an asset-credit ledger.** The mod metadata carries the author list — Azanor and GrigLog — with the credits field left empty (`mcmod.info` at the resources root); the changelog carries the release notes down to the BETA26 hotfix entry (`changelog.txt`); a dependencies file points at the Baubles jar version this build expects (`dependencies.info`); the language directory embeds an MIT licence file dated 2017 with the copyright holder blank (`lang/LICENSE`) and a readme pointing beta testers at the mod's issue tracker (`lang/README.md`). There is no per-asset attribution, no texture-credit file, and no asset-origin notes beyond these. Two caveats for the release lane: the metadata and the pack manifest are the two files the catalog records as content-differing between this tree and the shipped jar, and the licence file sits inside a language folder, which is where a port copying by resource kind may miss it.

26. **Delivery is a client resource pack shipped inside the mod jar, versioned by a pack manifest, and it interleaves with one vanilla namespace.** The payload's root manifest declares the pack and its format (`pack.mcmeta`, format 3, the 1.11-and-later value this tree targets), and the shader overlay under `assets/minecraft` replaces vanilla post-processing assets (four post descriptors and seven programs) — the one place a port must check for collisions with vanilla or other mods, and the one place whose files are legacy-format shaders that a 1.20-era port cannot copy verbatim ([cli-02-evidence.md](cli-02-evidence.md) finding 23 owns the pipeline those files feed). Everything else lives under the mod's own namespace and cannot collide.

27. **Nothing in this lane is dynamic: no asset syncs, no render state persists, and a second client or a late joiner needs only the same jar version.** The payload is static files; the only registration that runs on both sides is the sound-event registry (the sounds and sound types register through the common registrar's registry event, `Registrar.java:122-124`), and the files behind those ids are client-side resources — a server registers the events with no files and plays nothing itself. Entity renders reconstruct on each client from synced entities (the state they read is the owning lane's sync surface, [cli-02-evidence.md](cli-02-evidence.md) finding 24 records the same shape for FX); tile renderers read the client world's tile state. So: a second client inside view distance sees the same renderer outputs because it runs the same jar, a player who joins after an event sees the world as it currently is with no replay of anything, a resource reload swaps the payload wholesale with no partial state, and a port's asset work is verifiable per client with no server-side component — the acceptance's "client smoke" half needs one client and a log check, and its dedicated-server half needs only that the server never touches the payload.

## Rank-1 capture checklist

Reference setup for every step: the clean 1.12.2 profile whose only mods are the BETA26 jar and Baubles (`REF-0002` and the "Environment feasibility" section of [reference-catalog.md](reference-catalog.md)); a fresh creative world with its seed recorded in a new `REF` entry before the session. Creative mode supplies the whole item and block inventory and every spawn egg without research; the operator command `/thaumcraft research <player> <list|all|reset|<key>>` (`common/lib/CommandThaumcraft.java:72-80`, cited in [cli-01-evidence.md](cli-01-evidence.md)) unlocks anything a gate hides (the golem press parts are the likely case). Every step is bounded; stop at the bound even if the sample looks thin. Screenshots and short recordings are the evidence of record; anything countable should be counted off the images rather than asserted.

- **T1 — The payload sweep.** In one creative inventory pass, record the icon of every entry on the mod's creative tab and its sub-tabs, in enough batches to cover the item and block sets (the reference's own count is the bound: roughly three hundred item and block art files per finding 10; stop at one pass). Then place every device in the finding-10 block categories once — the jars, the tubes, the tables, the matrix, the lamps, the effect blocks — and record each device's model shape, including the invisible effect blocks (they should render as nothing) and the lamp stands when placed against a wall (finding 15). Bound: one icon pass, one placement per device class.
- **T2 — The entity sweep.** Spawn one of each of the forty-three registered entities (finding 21) and record each render once, in daylight and shade: note for each whether it uses a hand-built model, a vanilla-shaped model, or a code-drawn effect (finding 22's classes), and for the two size presets of the taintacle and seed note the scale difference. The warden and the eldritch golem are the two whose guardians share a model class. Bound: one spawn per entity, no combat.
- **T3 — The golem matrix.** Build or summon golems covering every part in the finding-9 registry: each head (five), each arm (four), each leg (four), each addon (three), and one of each material where the material shows (six). Record each part's model and its texture, and specifically whether the no-addon configuration shows anything where the registry's missing blank texture would bind (finding 9; the capture is the arbiter). Bound: one golem per distinct part, six materials on a single fixed configuration.
- **T4 — The model-mechanism set.** Record the mechanisms the JSON layer cannot express: the thaumometer held in first person, both hands, and in the GUI (the OBJ state file's transform set, finding 5); a jar's inventory icon at each fill level zero through four (the override chain, finding 7); a mirror in both states as an item; a shard ore's crystal shape in world (the bake swap, finding 11); a slab of each stone family in each half. Bound: one recording per mechanism.
- **T5 — The sounds.** Trigger each of the four block sound types by interacting with its blocks (a jar, a crystal ore, a flesh or taint block, a loot urn — finding 19), then the registered event set by category with the crafting and device blocks covering the most-referenced ids (start, fail, and wand tones on the matrix; the page and clack sounds in the book and screens). Record the shield charge interaction specifically: take a shielded hit and record what plays, if anything (the typo of finding 18 — silence is the expected finding). Bound: one trigger per sound type, one pass over the event set, one shielded hit.
- **T6 — The book and category art.** Open the research browser and record all seven category icons and each category's background page art (finding 12: the icons at `research/cat_*` and the seven JPG backgrounds), plus the knowledge-gain overlay and toast art the screens draw ([cli-01-evidence.md](cli-01-evidence.md) items 27-29 own the surfaces; this step photographs the art). Bound: one open per category, one knowledge gain.
- **T7 — Multiplayer, reload, and the client-only half.** With a second client: have it look at a jar, a golem, and a mob while the first client re-logs at the same spot — the renderer outputs should be identical, and the late client should see nothing replayed (finding 27). Run a resource reload (the pack reload key) and record that only shader-dependent visuals can change (finding 26). Then launch the dedicated server with no clients and confirm the console stays clean through a join, a jar interaction, and a golem order — the server must never load the payload (finding 27). Bound: one relog, one reload, one dedicated launch.
- **T8 — The negative list.** Confirm in-world that each enumerated hole is what the tree says: the pure-bucket item's icon (finding 6 — record what the game shows for it), the bore-trail and wand-beam visuals do not exist ([cli-02-evidence.md](cli-02-evidence.md) finding 6, with this lane's finding 13 note that their textures are gone too), the homing shard and rift blast never appear (finding 23), the golem no-addon entry shows or does not show a part (finding 9), and the shield charge sound is silent (finding 18). Then record that nothing in the payload is dynamically loaded — no asset is fetched at runtime beyond the shader set (finding 27). Bound: one observation per hole.
- The acceptance "No core BETA26 content uses placeholder or missing assets." fails on any count that disagrees with the findings: any creative-tab entry rendering as a missing-model placeholder, any spawn egg producing the missing-model shape, any device model swapped for a plain cube in the reference itself, or any sound in the reference's own trigger set that plays nothing where the findings say it plays.
