## Reference behavior (source-derived)

### A. The side model: two proxies over one shared base, and where the client-only code actually sits

1. **The side split is a three-class arrangement selected by one annotation.** `Thaumcraft.java:28` declares the sided proxy pair — client side `thaumcraft.proxies.ClientProxy`, server side `thaumcraft.proxies.ServerProxy` — over the nine-method contract in `proxies/IProxy.java:10-28`. `proxies/CommonProxy.java:46` implements that contract (with the GUI handler) for both sides; `proxies/ClientProxy.java:20` and `proxies/ServerProxy.java:7` extend it. The server subclass re-declares `preInit` as a pass-through (`proxies/ServerProxy.java:9-12`) and overrides `getWorld` through the dimension manager (`:14-17`). The client subclass adds the client-only work in its three phases — the OBJ loader domain and the shader pass in pre-init (`proxies/ClientProxy.java:32-37`), then colour handlers, key bindings, the entity renderer pass, and the tile renderer pass in init (`:39-46`), with the block-model registration at `:80-83`. Everything the mod does on both sides runs in the shared base's three phases (`proxies/CommonProxy.java:54-84`): the two capability registrations and the packet channel's `preInit` (`:58-60`), the player-knowledge and player-warp setup calls, the world-generator registration (`:63`), the GUI handler binding and the config/recipe phases (`:67-74`, `:76-84`).

2. **The base's client-facing methods return safe defaults, and the call census across them is nineteen sites.** `proxies/CommonProxy.java:94-103` answers the shift query with false, the client world with null, and model registration with an empty body; `getWorld` and `getSingleplayer` answer null and false (`:171-177`). A scripted count of the tree's `Thaumcraft.proxy` call sites finds nineteen `getClientWorld()` invocations across eighteen source lines (one line holds two), two `registerModel` calls, one `getSingleplayer`, and four lifecycle or inter-mod-comm dispatches — every one of them therefore a no-op or a null on a dedicated server. The nineteen reads sit inside clientbound handlers and client-side paths: the shield handler (`common/lib/network/fx/PacketFXShield.java:41-76`, seven reads), the infusion-source handler (`common/lib/network/fx/PacketFXInfusionSource.java:44`, `:47`), the sonic handler (`common/lib/network/fx/PacketFXSonic.java:36`, `:38`), the biome-change handler (`common/lib/network/misc/PacketBiomeChange.java:47`), the note handler (`common/lib/network/misc/PacketNote.java:64`), the seal pair (`common/lib/network/misc/PacketSealToClient.java:137`, `:141`, `:164` and `common/lib/network/misc/PacketSealFilterToClient.java:64`), and the tile handler (`common/lib/network/tiles/PacketTileToClient.java:43`). The two model registrations are inside the block-registration helpers (`common/config/ConfigBlocks.java:422-429` calling at `:430`; the class-argument overload `:431-443` calling at `:440`), so the same code path registers blocks on both sides and only the client proxy does anything with the item model. One contract method — the shift-key query — has **no caller anywhere in the tree**: a scripted search finds the interface declaration (`proxies/IProxy.java:24`) and the two implementations (`proxies/CommonProxy.java:94-96`, `proxies/ClientProxy.java:72-75`) and nothing else; the two client sites that need that answer call the vanilla screen class directly (`client/lib/events/RenderEventHandler.java:240`, `:266`).

3. **The @SideOnly census: 355 annotations in 259 of the tree's 895 Java files, and only sixty-three of them annotate a class.** Counts by top-level area: 221 in `common/`, 115 in `client/`, 14 in the vendored `codechicken/lib`, 3 in `api/`, and 2 in the root `Registrar.java`. 4. **Package-level split, checked three ways: client-only by package, client-only by content inside a shared package, and mixed.** Client-only by package: the whole `client/` tree, plus the vendored `codechicken/lib` helpers it draws on (its colour, render, raytracer, and vector classes carry 14 client annotations). Client-only by content inside a shared package: `common/golems/client` holds fourteen classes — the golem renderer, five part-model classes, the seal base container and screen, and six GUI buttons — of which only three carry an annotation at all (the renderer and the seal screen at class level, the seal container's progress-bar override at method level), and its own helper package `common/lib/events` holds the key handler, whose subscriber annotation is client-side and which is registered only from the client proxy's init (`proxies/ClientProxy.java:53-55`, class header `common/lib/events/KeyHandler.java:20`). The six block classes are the interesting case: they are blocks, instantiated on both sides, whose *subscriber registration* is client-only — so their client-typed members are the ones to keep behind the annotation, and the six are the first place a client-leak regression would show.

### B. The persistence surfaces: the NBT homes a reload must preserve

8. **The tile contract is one base class plus a sync half, and twenty tiles implement it.** `common/tiles/TileThaumcraft.java:42-56` chains the vanilla read into a sync half and the vanilla write into the same shape; the sync half is served by the vanilla update packet, whose build strips the two Forge keys before sending (`:63-81`), and the receive path feeds the sync half (`:68-70`); the block-update notify lives at `:58-61`. A scripted count finds twenty-four files implementing the read side (twenty of them tiles, four item-side) and twenty-eight implementing the write side. The inventory base adds the slot list and its guards (`common/tiles/TileThaumcraftInventory.java:171-186`).

9. **Representative tile pairs, one per persistence flavour a port must keep:** the crucible saves its tank and its aspect list through the sync half (`common/tiles/crafting/TileCrucible.java:68-83`); the mirror splits the sync half (linked state, link coordinates, and instability, `common/tiles/devices/TileMirror.java:233-256`) from the save half (the output stack list, `:299-320`); the infusion matrix saves the recipe's essentia in the sync half (`common/tiles/crafting/TileInfusionMatrix.java:146-162`) and the in-flight recipe stacks in the save half (`:165-219`); the pattern crafter (`common/tiles/crafting/TilePatternCrafter.java:55-74`), the arcane ear (`common/tiles/devices/TileArcaneEar.java:34-46`), and the focal manipulator (in the twenty-file list above) complete the set; the golem builder inherits its persistence from the inventory base (`common/tiles/TileThaumcraftInventory.java:171-186`) and is not among the twenty. The reload checklist's tile step is a sweep over this list, not over the full fifty-two tile classes: the tree's own answer to "which tiles persist" is the twenty-file list.

10. **Entity state is the same discipline with twenty-nine classes.** The three representative pairs: the golem writes its property long, home position, flag byte, rank experience, and colour, and rebuilds its attributes on read (`common/golems/EntityThaumcraftGolem.java:386-403`); the bore writes its charge, facing, and active flag (`common/entities/construct/EntityArcaneBore.java:483-497`); the rift writes its four size/stability figures and its collapse flag (`common/entities/EntityFluxRift.java:181-195`). The full read-side list spans constructs, monsters, bosses, the cultist family, tainted things, and projectiles — twenty-nine classes, enumerated by the scripted count — so "entities survive reload" is a statement about that list, and a fresh-world pass that spawns one of each of the forty-three registered entities (the count is [cli-03-evidence.md](cli-03-evidence.md) finding 21's) is the reload sweep's spawn half.

11. **Player-shaped state is two registered capabilities whose providers attach on entity attach and whose contents re-copy on the clone path.** The knowledge capability registers with Forge's capability manager in pre-init (`common/lib/capabilities/PlayerKnowledge.java:32-44`) and the warp capability identically (`common/lib/capabilities/PlayerWarp.java:22-34`), both delegating storage to their own NBT serialisation; the providers attach to every player at the attach event (`common/lib/events/PlayerEvents.java:367-370`); the warp's serialised shape is the three-element pool array plus the counter (`common/lib/capabilities/PlayerWarp.java:76-99`) and the knowledge's is its four stores (`common/lib/capabilities/PlayerKnowledge.java:205`, `:244`); a dimension change or respawn re-copies both through NBT with a logged catch (`common/lib/events/PlayerEvents.java:388-399`), and the join path re-pushes them (`:373-385`). What the fields mean is [ply-01-evidence.md](ply-01-evidence.md)'s (warp) and [rsr-01-evidence.md](rsr-01-evidence.md)'s (knowledge) — pointers only; this note records that the reload home exists and where it is written.

A whole-tree search finds no world-saved-data, per-world-storage, or map-storage class anywhere — the chunk tag is the only file the world state reaches. The aura triple's semantics and flush asymmetry are [wld-01-evidence.md](wld-01-evidence.md)'s findings 12-14 and item 20; the seal half is [aut-01-evidence.md](aut-01-evidence.md)'s findings 7-11; the marker's config default is `common/config/ModConfig.java:356`, `:388`.

### C. The fresh-world surfaces: what a world gets on creation and first load

14. **World creation runs one registered generator, and its first act per chunk is the aura seed.** The generator is registered at priority zero in pre-init (`proxies/CommonProxy.java:63`); its entry point runs the world-generation pass and then seeds the chunk's aura (`common/world/ThaumcraftWorldGenerator.java:48-51`), the pass is dimension-aware with the Outer Lands short-circuited (`:53-68`), and the content is split into the surface pass (mounds and the rare lesser cultist portal, `:71-94`), the vegetation pass (the two magical trees and the desert flower, `:106-123`), and the ore pass (cinnabar, quartz, amber, and the six shard ores with their aspect-driven metadata, `:125-213`), with the two tree helpers exposed for reuse (`:235-258`). The aura seed itself walks the biome's aura modifier across the five-sample neighbourhood and clamps the base (`common/world/aura/AuraHandler.java:166-182`). The content details are [wld-02-evidence.md](wld-02-evidence.md)'s and [wld-01-evidence.md](wld-01-evidence.md)'s; the scenario's job is to observe that a brand-new world gets them at all.

15. **Load-time initialization completes the fresh-world state on three hooks.** The world-load hook creates the dimension's aura cache (`common/lib/events/WorldEvents.java:21-25`) and the unload hook drops it and the dimension's seal layer (`:33-39`); the chunk-load hook restores or generates the chunk's aura and seals (finding 12); the regeneration worker drains ten queued chunks per world tick (`common/lib/events/ServerEvents.java:178-199`). Registration itself is ordered by the registry event callbacks — blocks (`Registrar.java:43-54`), items (`:56-67`), entities (`:69-72`), recipes (`:74-83`), potions (`:85-104`), biomes with their weights (`:107-118`), sounds (`:121-124`) — with two client-only passes riding the same events (`:50-53` blocks, `:63-66` items) that a fresh-world log review can confirm were skipped on a server.

16. **The per-world stores are static, dimension-keyed maps rebuilt on load — the reason a fresh-world run and a reload run can differ.** The aura handler's caches are three static maps created empty at class load (`common/world/aura/AuraHandler.java:22-24`), created per dimension on demand with an info log (`:41-46`) and removed at unload (`:48-51`); the seal handler's live map is the same shape (`common/golems/seals/SealHandler.java:32`, lazily layered per dimension at `:92-95`). Capabilities are the exception — they attach to the player entity and persist with it (finding 11). So the fresh-world scenario's initial-state checklist is: capabilities present on a brand-new player, biomes and spawns registered, the aura cache created and seeded per chunk on first load, an empty seal layer, and no leftover state from a previous world — which is the exact inverse of the reload scenario's "the state came back" question.

17. **What has no per-world store at all, and why the checklist lists it as a negative.** Nothing in this framework is written to a world-level file: no world-saved-data class exists (finding 12), the per-dimension caches are rebuilt (finding 16), and the registry content is static (finding 15). Whether the reference's own fresh-world behaviour matches that design — every seed, every store — is [wld-02-evidence.md](wld-02-evidence.md)'s and [wld-01-evidence.md](wld-01-evidence.md)'s content, and a "state survived a world that never had it" reading is a [wld-01-evidence.md](wld-01-evidence.md) item 22 divergence to look for, not this note's.

### D. The remote-client sync surfaces: one channel, forty classes, and what is pushed versus reconstructed

18. **The channel is one simple wrapper over one name, and the registration is a single block of forty-one calls over forty classes.** `common/lib/network/PacketHandler.java:96-98` creates the channel; `:51-94` holds every registration in one unbroken block. The census: forty-one register calls, forty distinct classes, the note packet being the one class registered on both sides (`:68` clientbound, `:72` serverbound); twenty-eight clientbound registrations over twenty-eight classes, thirteen serverbound over thirteen. By directory family: sixteen FX classes, all clientbound; fourteen misc classes carrying fifteen registrations (eight clientbound, seven serverbound — the note class supplies both); eight player-data classes (three clientbound, five serverbound); two tile classes, one each way.

19. **The clientbound families, mapped to their owning lanes (pointers only, no per-packet derivation).** The FX family's sixteen classes are [cli-02-evidence.md](cli-02-evidence.md)'s — its finding 14 records the family's handlers and trigger cadence and its finding 24 the radius each send uses. Knowledge and research state is [rsr-01-evidence.md](rsr-01-evidence.md)'s (its findings 16-19 own the two knowledge-sync directions, the progress-from-client packet, the flag packet, and the gain broadcast). Warp sync is [ply-01-evidence.md](ply-01-evidence.md)'s (its finding 35: the full state on join and the delta on change, applied client-local). Seals are [aut-01-evidence.md](aut-01-evidence.md)'s (its finding 11: the per-seal rebuild packet on every seal change and on every chunk watch). The aura readout is [wld-01-evidence.md](wld-01-evidence.md)'s (its findings 15-16: a point-to-point three-figure packet to the tool's holder). Foci config is [cas-03-evidence.md](cas-03-evidence.md)'s and the thaumatorium recipe selection and logistics requests are the device lanes' ([alc-04-evidence.md](alc-04-evidence.md), [aut-02-evidence.md](aut-02-evidence.md)). This note owns only the channel census those pointers sit in.

20. **What arrives at join, what arrives on change, and when.** Two server-side paths push the player's own state at a connection: the login handler sends the warp and knowledge snapshots (`common/lib/network/EventHandlerNetwork.java:19-26`) and the entity-join handler does the same for every joining player entity (`common/lib/events/PlayerEvents.java:373-385`); later changes re-push through the capability's own sync entry points (`common/lib/capabilities/PlayerWarp.java:72-74`, `common/lib/capabilities/PlayerKnowledge.java:201-203`). Tile state travels three ways — a broadcast to everyone within one hundred twenty-eight blocks, a point-to-point send, or the vanilla tile update packet (`common/tiles/TileThaumcraft.java:21-30`, `:27-29`, `:63-74`) — and the client applies it to the local tile through the message hook (`:36-40`). Seals are pushed per chunk to a watching player (`common/lib/events/ChunkEvents.java:92-97`). The remote-client scenario therefore has four arrival times to separate: at join, at change, at chunk watch, and on the tile tick.

21. **What the client reconstructs locally instead of receiving.** FX are draw-only broadcasts ([cli-02-evidence.md](cli-02-evidence.md) finding 24); models, textures, sounds, and entity renders are client resources reconstructed per client from the same jar ([cli-03-evidence.md](cli-03-evidence.md) finding 27); screens are built from container state ([cli-01-evidence.md](cli-01-evidence.md)); the particle engine's stores are per-process and per-dimension ([cli-02-evidence.md](cli-02-evidence.md) finding 25). The scenario distinction that matters: a missing packet shows up as a wrong figure on a screen or a stale tile, while a reconstructed visual shows up as nothing — so the remote-client pass must check state on screens and tooltips, not just what renders.

22. **The serverbound half is clean, and the serverbound payloads are all player-intent messages.** All thirteen serverbound classes reference no client package at all (a scripted check), and their families are the focus configuration pair, the item key, the misc string, the logistics request, the recipe selection, the note packet, the player flag, the progress and research-flag writes, the tile message, and the focus-change packet (`common/lib/network/PacketHandler.java:56-77`). Their semantics are the owning lanes' ([cas-03-evidence.md](cas-03-evidence.md), [rsr-01-evidence.md](rsr-01-evidence.md), [alc-04-evidence.md](alc-04-evidence.md), [aut-02-evidence.md](aut-02-evidence.md)); this lane records only that a dedicated server's receive side is client-free by construction.

23. **The channel's one client-typed risk is the six classes of finding 6(b), and the acceptance's dedicated-server clause is the probe for it.** Seventeen of the twenty-three client-referencing clientbound classes carry an annotation; the six that do not are the pollute, block-arc, block-mist, aura, item-to-container, and tile-to-client classes. Everything else about the remote-client story — ordering, freshness, reconnection — is a T7 observation.

## The four-scenario protocol (rank-1 capture checklist)

Reference setup for every step: the clean 1.12.2 profile whose only mods are the BETA26 jar and Baubles (`REF-0002` and the "Environment feasibility" section of [reference-catalog.md](reference-catalog.md)); a fresh creative world with its seed recorded in a new `REF` entry before the session, following `REF-0005`'s shape (launch spans, world names and seeds, player-setup state, and any environment deviation recorded up front); a second client and a dedicated-server launch available for the multiplayer and server steps, with the EULA caveat below standing. Creative mode supplies the item, block, and spawn-egg inventory without research; the operator commands are the reload verb (`common/lib/CommandThaumcraft.java:64-69`) and the research and warp verbs whose help lines are printed by the command itself (`:73-79`), and every command write is a measurement input — use them between measurements only and record each use. Screenshots and short recordings are the evidence of record; counts come off the images. Every step below is bounded; stop at the bound even if the sample looks thin. The promotion workflow runs after the session (below the steps).

- **T1 — The fresh-world genesis.** Create the world from the menu with the seed recorded, and before touching anything record: the world loads with no error in the log; a brand-new player's screens work (the research browser opens, the inventory holds the mod's creative tabs); and the aura readout responds on the first chunk the player stands in (finding 16's initial-state list, observed rather than assumed). Bound: one world creation, one log pass, one readout.

- **T2 — What the fresh world contains.** In a bounded radius around spawn, record one of each world-generation class the tree promises: a shard-ore cluster with its aspect-driven variant, cinnabar, quartz, and amber ore blocks placed, a greatwood and a silverwood tree (grow a sapling to avoid the surface-search bound where one is not visible — the growth path is [wld-02-evidence.md](wld-02-evidence.md)'s), the desert flower if a hot sandy biome is in range, and the biome names themselves (finding 14). Then confirm the spawn set: a representative hostile (a wisp or a cultist) spawns naturally over a bounded night (the spawn registration is [wld-05-evidence.md](wld-05-evidence.md)'s). Bound: one sample per generation class, one night.

- **T3 — The reload conservation sweep (the acceptance slice).** In the same world, set up one artefact per persistence home and record its exact state: a crucible holding a measured aspect amount (tile tag), a spawned golem given a part set and a rank (entity tag), a player with warp set and a research grant (capability tags), a placed seal with a non-default priority (chunk tag), and a caster carrying a configured focus in the inventory (item-stack tag) — then save and quit, relaunch, re-enter, and read each of the five back against the recording (findings 8-13). Bound: five artefacts, one save/quit/relaunch.

- **T4 — The chunk unload and reload pass.** With T3's artefacts in place, walk far enough to unload the chunks (or use a teleport), return, and re-read the block-entity and seal artefacts — the validation matrix's persistence tier names this pass explicitly. Then repeat the same read after a full stop and restart to separate the unload path from the save path (finding 12's unloaded-chunk branch is the mechanism). Bound: one walk-away, one restart.

- **T5 — The kill pair.** Re-set one drained aura figure and one in-flight device, then hard-kill the game or the server process before the next save wave, restart, and record both sides: whether the world-side figures returned and whether the product of the drain (the cast's effect, the item's charge) survived. Neither side alone is the measurement — the asymmetry is [wld-01-evidence.md](wld-01-evidence.md) item 20(a)'s, and this step is its framework-level twin. Bound: one kill.

- **T6 — The dedicated server with no clients (the acceptance's crash property).** Launch the dedicated server against a fresh server directory with no client attached, then attach one client, join, and exercise the surfaces finding 6 lists: receive each of the six unannotated clientbound classes at least once (the aura readout, a tile message from an opened device, an item-to-container update, and one cast each of the arc, mist, and pollution FX), place and configure a seal and a golem, and give the golem a harvest order (the fake-player path, finding 7). Record the server console and log throughout; the acceptance fails on any server-side exception or client-caused error in that pass. Note the gate: the catalog records no accepted EULA anywhere on the machine, so this step runs only after the owner accepts it ([reference-catalog.md](reference-catalog.md), [budget-hold.md](budget-hold.md)). Bound: one launch, one join, one of each surface.

- **T7 — The remote client, the reconnect, and the arrival times.** With two clients on the server, have the second client join *after* the first has set up state, and record what it sees at join: the first client's research and warp figures (screens only — the gauge and pages), a tile's synced state, a placed seal, and the aura readout after the tool is held (finding 20's four arrival times). Then have the second client reconnect mid-session and re-read the same four items; then have it act (open a device screen, cast once) with the first client watching, recording the visible outcome on the other client. Bound: one join, one reconnect, one watched action per arrival class.

- **T8 — The negative list, run as attempts.** Confirm in-world, one attempt each: that the six unannotated packet classes produce no server-side error when their payloads are sent (T6 covers reception; this step records the send side from play); that the golem with each part configuration of the registry shows its part (the registry's static block is finding 6(c), and the parts' looks are [cli-03-evidence.md](cli-03-evidence.md) finding 9's); that a player holding no tool sees no aura figure at all (the readout is holder-only, [wld-01-evidence.md](wld-01-evidence.md)); and that a fresh world's stores read empty rather than stale (finding 17). Anything an attempt contradicts overrules the source read — that is the point of the step, not a failure of it. Bound: one attempt per item.

- **The promotion workflow (how a rank-3 item becomes rank-1).** Run the step; capture the observed behavior as a new `REF` entry with every required field, following the catalog's recording steps 1-5 (capture the artifact digest by its convention, keep the recording outside the repository, then link the identifier from the work item's note) ([reference-catalog.md](reference-catalog.md)); then return to this note and promote or correct the specific finding the step covered — a confirmed item loses its rank-3 qualifier in the evidence table and gains the `REF` identifier, a contradicted item is corrected in place with the capture as its new basis, and an unrun item is recorded as `not-run` rather than left implicit. The sibling checklists already point their multiplayer and reload steps at this procedure ([aut-01-evidence.md](aut-01-evidence.md) T7, [aut-02-evidence.md](aut-02-evidence.md) T7, [cas-03-evidence.md](cas-03-evidence.md) T6, each marking it the same gap), so a completed T6 becomes the shared answer for those lanes too.
- **The acceptance failure condition.** The workboard's quality bar — "a fresh survival world reaches all major systems without commands; systems survive save/reload and dedicated-server multiplayer; no known crash, dupe, data-loss, or progression deadlock remains" ([parity-workboard.md](parity-workboard.md)) — fails for this lane on any T3 or T4 item that comes back different from its recording, any error in T6's server log during the exercised pass, any T7 arrival that never arrives, or any T1/T2 step whose fresh world does not contain what finding 14 and finding 15 promise.
