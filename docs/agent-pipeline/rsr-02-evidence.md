## Target behaviors to capture

From the evidence-index queue row for `RSR-02` (Arcane Workbench crystal/Vis/research checks and atomic crafting consumption) and the workboard acceptance line ("insufficient resources never craft; valid craft consumes exact resources across client/server"):

1. **Research gate** — which research form an arcane recipe requires before its result may appear.
2. **Vis gate** — how the workbench's available Vis is read, how the cost is computed, and what happens when the two disagree.
3. **Crystal gate** — which items satisfy a crystal requirement, how many, and where they must sit.
4. **Result computation** — what the result slot holds, on which side it is decided, and the fallback path.
5. **Consumption order and exactness** — the order of Vis, ingredient, and crystal consumption, and the amounts.
6. **Atomicity** — what happens when a resource changes between result display and take.
7. **Persistence** — what the workbench stores and what dropping it returns.

## Reference behavior (source-derived)

### A. Container construction and slot layout

1. **The block opens a server-side container; the client only asks.** `common/blocks/crafting/BlockArcaneWorkbench.java:33-39` returns early on the client and otherwise opens the mod GUI with id 13 at the block position. Breaking the block drops the whole craft inventory (`:42-49`), including the six crystal slots.
2. **The craft inventory is a 5×3 crafting matrix, i.e. 15 slots.** `common/container/InventoryArcaneWorkbench.java:12-15` constructs an `InventoryCrafting` of width 5 and height 3 and implements the marker interface `api/crafting/IArcaneWorkbench.java:10-12`; `markDirty` forwards to the owning tile (`common/container/InventoryArcaneWorkbench.java:21-24`).
3. **Slot map.** `common/container/ContainerArcaneWorkbench.java:45-73`: result slot at index 0, backed by `SlotCraftingArcaneWorkbench` at (160, 64); the nine 3×3 grid slots at indices 1-9 with 24-pixel spacing; six `SlotCrystal` slots at indices 10-15, created by iterating `ShardType` values whose metadata is below 6 and positioned from the static `xx`/`yy` arrays (`:227-230`); the player inventory and hotbar afterwards. The constructor ends by computing the result (`:72`).
4. **Crystal slots are aspect-locked.** `common/container/slot/SlotCrystal.java:18-24` accepts a stack only when it is a crystal essence item whose first (single) aspect equals the slot's aspect; shift-click routing applies the same test (`ContainerArcaneWorkbench.java:182-194`). The six slots correspond to the six primal shards, since `common/blocks/world/ore/ShardType.java:8-16` lists metadata 0-5 as air, fire, water, earth, order, and entropy, with flux at 6 and therefore excluded.
5. **The result slot cannot be inserted into, and tallies what was crafted.** `common/container/slot/SlotCraftingArcaneWorkbench.java:41-43` refuses insertion; `:45-50` accumulates the crafted amount; `:61-73` fires the vanilla crafting event path and unlocks the recipe for the player when the recipe is not dynamic.
6. **The container forwards only one integer to the client.** `common/container/ContainerArcaneWorkbench.java:75-79` sends window property 0 with the tile's server-side aura value when a listener is added, and `:100-105` writes that value into the tile's client field when the client receives it. The tile's own sync NBT methods are empty (`common/tiles/crafting/TileArcaneWorkbench.java:49-56`), so the Vis figure the client displays comes exclusively from this window property.

### B. Gates

7. **The result path has two gates, and the research gate lives only in the server branch.** `ContainerArcaneWorkbench.java:107-132` recomputes the recipe on every matrix change; if a recipe matches, it derives the Vis cost (`:114-115`), derives the crystal list (`:116`), compares the cost against the cached aura — client value on the client, server value on the server (`:118`) — and runs a strict count test for each required crystal over the wrapped 15-slot inventory (`:119-126`); the result is computed only when both pass (`:128-130`). The server branch that actually fills the result slot (`:134-157`) additionally requires that the player knows the recipe's research key, and otherwise falls back to a vanilla 3×3 match over a copy of the nine grid slots (`:139-152`) before pushing the stack to the player with a slot update (`:154-155`). Note that crystal/VIs gating is applied before the research check, and the research check uses the knowledge test that also honours `@stage` forms.
8. **The cost formula truncates the discount factor.** `:115` and the mirror in the take path (`common/container/slot/SlotCraftingArcaneWorkbench.java:96-97`) compute the cost as the recipe's Vis multiplied by the integer value of one minus the player's total Vis discount; the same expression is used for the number the GUI prints (`client/gui/GuiArcaneWorkbench.java:59-63`). `common/items/casters/CasterManager.java:26-40` computes that discount from Baubles and armor items implementing the Vis-discount interface. Consequence as written: any non-zero discount yields a factor of zero. Whether the released build behaves that way is **unverified — needs rank-1 observation** (checklist S4).
9. **Crystal sufficiency is a count over the whole craft inventory, using a constructed comparison stack.** The test builds a crystal stack for the aspect and required amount through `api/ThaumcraftApiHelper.java:314-319` (crystal essence item, single aspect, requested count) and counts matching stacks with the strict filter variant of `api/ThaumcraftInvHelper.java:202-212`, which sums matches anywhere in the wrapped handler. A stack of the right aspect counts regardless of which aspect-locked slot holds it; only the six crystal slots are inside the wrap.
10. **The aura reading has two modes.** `common/tiles/crafting/TileArcaneWorkbench.java:58-78`: when the block directly above is the workbench charger, the available Vis is the sum of the nine surrounding chunks' Vis values, each individually truncated to an integer; otherwise it is the Vis of the single chunk at the block position, also truncated. `common/world/aura/AuraHandler.java:79-82` reads the chunk's Vis. So the displayed cost comparison is integer-vs-float with the available side already floored.
11. **Spending is best-effort and its shortfall is never surfaced.** `TileArcaneWorkbench.java:80-109`: with a charger above, the cost is split across the nine chunks with an even share computed once (`:84`) and re-clamped per iteration, and the drain primitive is asked with simulate=false; each call's drained amount is subtracted from what remains so the loop keeps retrying (`:94`), and the loop gives up after 1000 attempts; without a charger, a single drain call at the block position whose return is discarded (`:106`). `AuraHandler.drainVis` (`common/world/aura/AuraHandler.java:120-131`) clamps the request to the chunk's available Vis and reports the amount actually drained (`:130`); the workbench's spend method never surfaces the drained-vs-requested shortfall to its caller, and neither the container nor the result slot re-checks affordability when the result is taken. A shortfall therefore reduces the Vis consumed without blocking the craft — this is the central atomicity question for the port and it is **unverified — needs rank-1 observation** (checklist S6).
12. **Recipe lookup performs no research filtering.** `common/lib/crafting/ThaumcraftCraftingManager.java:76-99` walks the recipe registry and returns the first `IArcaneRecipe` whose vanilla `matches` succeeds; research is applied only by the container's result path (item 7). Lines `:77-91` compute a first/second non-empty stack and a count that are never read afterwards — an implementation artifact, not a behavior. Helper wrappers return the result, crystal list, and Vis for a matched recipe (`:101-114`).
13. **The recipe contract and the shipped implementations.** `api/crafting/IArcaneRecipe.java:1-11` declares exactly three additions over a vanilla recipe: a Vis cost, a crystal aspect list, and a research key. The tree ships `api/crafting/ShapedArcaneRecipe.java:19` and `api/crafting/ShapelessArcaneRecipe.java:19`, which extend the Forge shaped and shapeless ore recipes, so the 3×3 matching and mirroring behaviour of ordinary vanilla recipes applies to the grid slots.

### C. Take path: order and exactness

14. **The take path re-derives everything and then consumes in a fixed order.** `common/container/slot/SlotCraftingArcaneWorkbench.java:75-136`:
    - re-finds the matching arcane recipe against the live matrix (`:77`);
    - collects the remaining items, using the real matrix when an arcane recipe matched and a dummy copy of the nine grid slots otherwise (`:79-91`);
    - computes the Vis cost with the same discount expression and, only when the cost is greater than zero, calls the tile's spend method (`:96-102`) — **Vis first**;
    - then walks the nine grid slots, decrementing each occupied slot by one and re-inserting or growing the remaining item (`:104-123`) — **ingredients second**;
    - then, for each required aspect, builds the matching crystal stack and decrements any of the six crystal slots whose item and tag match by the recipe's per-aspect amount (`:124-134`) — **crystals last**.
15. **Exactness caveats visible in the same method.** The crystal loop decrements by the recipe's required amount per matching slot with no sufficiency re-check, so a stack smaller than the required amount is consumed to zero without complaint; and because the Vis spend happens before ingredients and crystals, a take that somehow fails later in the method would already have paid the Vis. Both are source-derived readings of the order, not observations.
16. **The result slot is emptied by the vanilla take path**, so the "consumed exactly once" property depends on the slot machinery rather than on the workbench code; the crafting event and recipe-unlock bookkeeping happen in `onCrafting`/`decrStackSize` (`:45-73`).
17. **The matrix-change path is throttled.** `ContainerArcaneWorkbench.java:81-98` refreshes the tile's aura at most every 500 ms, recomputes the result whenever the last-sent Vis value differs from the current one, and pushes the property to every listener when it changed. So the result slot can be up to one refresh interval stale relative to the world's aura. **Unverified — needs rank-1 observation** for how that presents in play.

### D. Persistence and early-game context

18. **The workbench stores its 15 slots in NBT and nothing else.** `common/tiles/crafting/TileArcaneWorkbench.java:29-47` loads and saves the craft inventory through the standard item-list helpers; no Vis value is stored (item 6). `ContainerArcaneWorkbench.java:159-164` swaps the matrix's change handler back to a dummy container when the container closes.
19. **The GUI exposes the gates to the player.** `client/gui/GuiArcaneWorkbench.java:55-65` recomputes the cost and crystal list client-side, `:66-82` draws a coloured rune ring over each required crystal slot (aspect colour and slot position taken from the same static arrays as the container), `:85-89` prints the available Vis with a colour change when it is below cost, and `:92-119` prints the cost and the discount percentage and renders a greyed ghost of the result while the available Vis is below cost. These are the observables the checklist below reads.
20. **Early-game recipe context for the checklist.** `common/config/ConfigRecipes.java:187` registers an arcane recipe for the activator rail at 10 Vis under research `FIRSTSTEPS`, and `:188` registers the Thaumometer at 20 Vis with one crystal of each primal aspect under `FIRSTSTEPS@2` — a recipe whose research key requires a stage, making it the natural subject for the research-gate check. `:73-74` registers the arcane workbench block as the result of a dust trigger on a crafting table; that trigger is valid only when the player already knows `FIRSTSTEPS@1` and its execution swaps the target block for the result (`common/lib/crafting/DustTriggerSimple.java:29-44`), so it grants the block rather than the research. The research JSON that defines those stages is outside this note.

## Rank-1 capture checklist

Reference setup as for [rsr-01-evidence.md](rsr-01-evidence.md): a clean 1.12.2 instance with only the BETA26 jar and Baubles, fresh world, recorded seed, and a new `REF` entry before the session. `/thaumcraft research <player> <list|all|reset|<key>>` (`common/lib/CommandThaumcraft.java:59-113`, op-only) is the setup lever for the research gate; it must not be used while a measurement is being taken.

- **S1 — Research gate on an `@stage` key.** With research granted only to the parent stage (no `FIRSTSTEPS@2`), place the Thaumometer recipe in the grid with its crystals: confirm the result slot stays empty. With the research known and its stage at or past the recipe's requirement, confirm the result appears without touching the grid. Confirms item 7 and that the stage form is enforced. Note that the grant form of the operator command adds the entry **and its parents** and drives them to complete (`common/lib/CommandThaumcraft.java:181-215`), so it cannot create a partially-staged state: the low-stage half of this check must be reached by play during natural progression; the command is useful only for the unknown-research half and for the cleanup (`revoke`).
- **S2 — Crystal gate, positive and negative.** For a recipe with a crystal list: with no crystals, confirm no result; insert exactly the required count of each aspect, confirm the result appears; remove one crystal, confirm the result disappears; insert a crystal of the wrong aspect, confirm the slot rejects it and that shift-clicking the wrong crystal routes it to the inventory rather than a crystal slot. Confirms items 4, 7, and 9.
- **S3 — Vis gate.** In a chunk with low aura (or after draining it by repeated crafting), place a recipe whose cost exceeds the available Vis and confirm the result slot stays empty, the available-Vis readout changes colour, and a greyed ghost of the result is drawn — then wait for the aura to regenerate and confirm the result appears on its own. Confirms items 7, 10, and 19.
- **S4 — Discount interaction.** Record the displayed cost and the discount percentage for the same recipe with and without a Vis-discount Bauble or armor piece equipped. The source expression in item 8 predicts the cost reads zero with any discount; record the actual numbers, since this is the one place the source may not match the shipped jar.
- **S5 — Consumption exactness, all three resource classes.** Take a result and verify: the grid ingredients each drop by exactly one, the crystal slots each drop by exactly the recipe's per-aspect amount, the aura drops by the displayed cost, and the result count matches what the recipe yields. Repeat with a crystal slot holding more than the required amount and confirm only the required amount is consumed. Confirms items 14 and 15.
- **S6 — Atomicity probe (the key one).** With a result displayed for a recipe whose cost equals the available Vis, change the world so the aura falls below cost — the bounded levers are a second player consuming aura in the same chunk, or removing/adding the workbench charger so the tile switches between the nine-chunk sum and the single-chunk read — and then take the result within and after the ~500 ms refresh window. Record: whether the result slot empties, whether the craft still completes, and how much Vis is actually drained. This decides item 11, which is exactly the question the port's "not fully atomic" defect rests on.
- **S7 — Persistence and drops.** Fill the grid and all six crystal slots, quit and reload: confirm all 15 slots persist. Break the workbench: confirm every stack, crystals included, drops. Confirms items 1 and 18.
- **S8 — Multiplayer agreement.** With two clients at one workbench, confirm both see the same Vis readout and the same result slot, and that one client taking the result removes the resources exactly once for both. Confirms items 6, 14, and 16.
- **S9 — Vanilla fallback.** Place a plain vanilla 3×3 recipe (no arcane recipe matches) in the grid with a known arcane-research-free context and confirm the workbench produces it, which is the observable form of the fallback at item 7.
